# IPC channel inventory

> Language: English · [中文](../zh/ipc-channels.md)
> Scope: the complete IPC channel inventory (58 channels in total), grouped by category. Read this before changing IPC. The single source of truth for the constants is `packages/shared/src/types/ipc.ts`; the preload-side constants are generated by `scripts/generate-preload.cjs` (run `pnpm generate:ipc` after editing), and `scripts/verify-ipc-sync.cjs` checks during lint that the generated artifact is not stale.

### Presets (5)

Preset files live in `~/.llama_launcher/presets` (decoupled from the models directory as of 2026-10-08; the legacy `<models_dir>/presets` is migrated automatically at startup). The primary key is a stable id — renames and moves no longer invalidate references. All reads and writes go through core's `PresetRepository`; the channel payloads never expose directories or file layout.

| Channel | Purpose |
| --- | --- |
| `presets:list` | Preset list (payload `PresetSummary[]`: a lightweight summary of id/name/timestamps/bound model, **without values** — this is the full extent of what the presentation layer knows about a preset) |
| `presets:save` | Save a preset (upsert, payload `{ name, values, id? }`: no id = create by name, an existing same-name preset is overwritten (its id and created_at are inherited); with id = update that preset (rename allowed); returns the persisted summary) |
| `presets:load` | Fetch the full preset (with values) by stable id; null when absent |
| `presets:rename` | Rename (id stays constant, only the display name changes; collisions/missing targets surface as `preset-name-exists` / `preset-not-found`) |
| `presets:delete` | Delete by primary key; true when a file was deleted |

### Server (6)

| Channel          | Purpose                                         |
| ---------------- | ----------------------------------------------- |
| `server:start`   | Start the service                               |
| `server:stop`    | Stop the service                                |
| `server:restart` | Restart the service                             |
| `server:status`  | Query service status (accepts `refresh?: boolean`: when true it also kicks off a /props re-check without blocking this reply (the auto-refresh metronome lives in the renderer: it only knocks while the page is visible and backs off when idle — see core-modules §re-check); returns `ServerInfo`: status + pid + host/port/url + the `values` snapshot + the `stop` stop-fact + `envOverrides`, the `LLAMA_ARG_*` variable names detected at launch + `propsCheck`, the read-back reconciliation + `readyAt`, the readiness moment); the main process also **pushes** `ServerStatusEvent { status, stop, propsCheck, readyAt }` on this channel — `stop` (`ServerStopInfo`) is the sole basis for the UI telling "Stopped / Failed / Crashed" apart; `propsCheck` arrives via **a second event with the same status** after readiness (the read-back is async and must not block the transition; the renderer handles status idempotently) |
| `server:preview` | Preview the launch command                      |
| `server:output-batch` | Output push (main process → renderer), **payload is an `OutputEntry[]` array**: lines within a 16ms window are merged into a single message |

### System (11)

| Channel               | Purpose                                                                                                                  |
| --------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `system:checkPort`    | Check whether the port is taken (probed at the `--host` address llama-server is about to bind; default 127.0.0.1, and for 0.0.0.0/LAN IPs the corresponding address — measured 2026-09: when the holder binds a LAN IP, probing 127.0.0.1 misses while probing that address hits, which covers holders on other network interfaces; from b11178 `--host` accepts comma-separated multiple addresses, so the probe now runs **every** TCP address returned by `tcpHosts()` in parallel and treats the port as taken if any one of them cannot be bound, while `.sock` entries take no part in TCP probing and only an unset host falls back to the default address; on Windows a wildcard and a loopback binding can coexist, so the probe is best effort; when occupied it returns the holder's PID/process name) |
| `system:killProcess`  | Terminate the specified process (port-conflict handling: Windows `taskkill /F /PID`, POSIX SIGKILL; invoked only after the renderer side has confirmed) |
| `system:findFreePort` | Scan forward from the given port and return the first free one (host semantics identical to checkPort: with multiple addresses a port counts as free only when **every** TCP address can bind it, since a partial bind would fail the launch; returns null when none is available) |
| `system:estimateVram` | VRAM probe + context capacity estimate (spawns `llama-server --list-devices` to get free VRAM per device + the GGUF KV memory model to estimate the full-offload context ceiling + performance-target linked suggestions; the exe used for probing is resolved by core's `resolveServerExe` with stepwise fallback (`server_exe` → same directory → `llama_dir` and its first-level subdirectories → dev-mode `llama-*-bin-*`), so renaming or moving the engine directory does not fail silently; best effort — failed fields are null and the reason comes back on `probeError` (including the paths that were tried); the 30s device-probe cache **stores successful results only**, resetting the timestamp on failure so a corrected directory re-probes immediately; results are cached for 60s keyed by model\|dtype\|target\|ngl\|ctxSize) |
| `system:benchLlamaRun`    | Start the llama-bench offline health check (pp512/tg128 full offload, fire-and-forget, one job per model; results cached by model path and written to `bench-records.json` on a terminal state so they survive a restart) |
| `system:benchLlamaStatus` | Read the health-check job status/result (running/done/error + LlamaBenchSummary); **used only to resync state when the tab becomes visible again** — live updates arrive via the push below. The main process cache is rehydrated from the on-disk records, so asking about a model after a restart still returns its previous result |
| `system:benchOnStatus` | **Main-process push** of health-check job state transitions (`LlamaBenchJobState`): completion happens in a main-process promise callback, so one push suffices — previously the renderer polled this status every 2.5s, turning a known event into a recurring question |
| `system:estimateModelFit` | Batch VRAM-fit verdict for the model list (fit/partial/no badge + the full-offload context ceiling; verdict is null when the metadata cannot be read) |
| `system:fileExists`   | Check whether a file exists                                                                                          |
| `system:findLlamaExe` | Find the llama-server executable in a directory (inline detection)                                                   |
| `system:detectTrash`  | Detect cleanable items among app-generated files (dual-root scan of the config directory + the model directory; paths of active/paused/retryable download tasks are protected automatically) |
| `system:cleanTrash`   | Perform the cleanup (each item is re-validated for root ownership, kind signature, the protected set and symlinks)  |
