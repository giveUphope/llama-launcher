### 5.1 Parameter definitions (shared/params/definitions.ts)

- **`PARAM_GROUPS`**: 3 groups — `basic` / `advanced` / `server`.
- **`PARAMS`**: 69 parameters in total, distributed as follows:
  - basic: 26 (19 core + 7 sampling)
  - advanced: 29 (5 thinking control + 10 speculative decoding (of which **4** carry `dependsOn.values` depending on an external draft type draft-simple/eagle3/dflash/dspark, while the other 2, `spec_draft_n_max`/`spec_draft_n_min`, use `notValues: ['', 'none']`, i.e. any non-empty type satisfies them) + 6 multimodal + 6 KV extensions + 2 template)
  - server: 14 (2 identity/auth + 4 endpoints + 4 CORS + 4 runtime behavior)
- Each parameter definition carries fields such as `key, group, type, flag, default, subcategory, dependsOn, ggufField, invert_flag`.
- **The two kinds of "default" must be kept apart** (`params/engine-baseline.ts`, split out on 2026-09-25): `ParamDef.default` is the **initial UI value** (it carries the launcher's baseline recommendations, e.g. `-ctk q8_0`, `--load-mode none`, `--fit off`); the basis for the emission decision is a different concept, **`engineDefault` = what `llama-server` does when it never receives that flag**, taken entry by entry from the help baseline. Mixing them up meant a recommendation that happened to equal `default` never reached the command line — the engine ran its own default while the UI displayed the recommendation. The table also holds `sentinel` (values explicitly meaning "unspecified, never emit", e.g. `chat_template`'s `none`) and `note` (mandatory whenever `default ≠ engineDefault`, explaining why the engine default is overridden). **The key set must equal `PARAMS` in both directions and `engineDefault` is cross-checked against help — both are hard-gated by `verify-params-sync.cjs`.**
- **8 control types**: `text` / `int_slider` / `int_entry` / `float_slider` / `dropdown` / `checkbox` / `file` / `dir`.
- **ggufField mapping**: a parameter may declare a `ggufField` mapping onto a field of `GgufModelInfo`, so the model's built-in value is shown inline on the parameter row; `buildSuggestions` derives suggested parameters from the metadata and one click applies them. The mappings are classified by actual purpose (reviewed 2026-09): only **deterministic factual mappings** (`nextn_predict_layers → spec_type` sampling recommendations, etc.) and **heuristic rules** (quantized weights → KV q8_0, etc.) produce suggestions; **pure reference information** (`context_length` training limit, `rope.freq_base`, etc.) is displayed inline / on the information card only and produces no suggestion (`-c` default 0 = loaded from the model, so per-item suggestions are a source of confusion); `cache_type_k/v`/`jinja`/`alias` had their semantically wrong ggufField entries removed.
- **VRAM occupancy estimate and performance targets**: core `devices.ts` (VRAM probing via `--list-devices`) + `vram-estimate.ts` (the KV memory model with two-sided VRAM/memory occupancy `estimateOccupancy`, plus the largest OOM-free context solver `solveMaxContext`) + `target-recommend.ts` (cascade suggestions for the four performance target tiers), exposed through `system:estimateVram`; the "VRAM usage (est.)" stat and the target picker on the Params page status bar are the only UI entry points (see frontend §7.3 / the module table in core-modules §4).

### 5.2 Dual-track parameter mechanism (session / presets)

Parameters have **no independent enable/disable state** — the rule for emitting a command-line flag is "emit only when value ≠ the **engine default** (`engineDefault`), and the value is not one of that parameter's `sentinel` values" (a checked checkbox emits `flag`, an unchecked one emits `invert_flag`, a default-false switch without an `invert_flag` emits nothing when unchecked; empty strings are skipped; unmet dependencies are skipped — see [core-modules.md](core-modules.md) §4.3); the legacy `_enabled` JSON enablement mechanism was removed together with the old logic and replaced by the dual-track one (`buildCommand` ignores a legacy `_enabled` it happens to read).

- **Read-back verification (since 2026-09-26)**: "emit only when the value differs from the engine default" rests on two prerequisites the UI cannot see — the engine's default may differ from the baseline we recorded (cross-version drift), and the user's environment may carry `LLAMA_ARG_*` variables that rewrite it. So after readiness core fetches `GET /props` and reconciles the engine's **actually effective** values item by item, and re-checks on demand (when the tab becomes visible again, or the user clicks "re-verify"; an event is re-emitted only when the result actually changes, and `checkedAt` states the freshness). The map and comparison live in `shared/params/props-mapping.ts`; see [core-modules.md](core-modules.md) §4.11 — a live measurement covers **14 mapped / 13 checked / 0 false alarms**, the other ~50 parameters are not reported by the engine, which is why the command preview card **speaks only on a real mismatch** and never implies "everything was verified". The same channel also compares `build_info` against the constant `ENGINE_BASELINE_BUILD` (the engine build the baseline is pinned to) and warns that the baseline may be stale.
- **Session track (temporary)**: every parameter edit is persisted automatically into `session_values` + `session_baseline` in `~/.llama_launcher/settings.json` (the `autoSave` watch with an 800ms throttle, **writes settings only, never preset files**); at app start `restoreSession` restores the last session (parameter values plus the baseline together).
- **Preset track**: `<models_dir>/presets/*.json` is written only when the user explicitly saves a preset; applying a preset (`applyPreset`) establishes a new session baseline as "preset name + parameter snapshot" (`markBaseline`).
- **Baseline**: `SessionBaseline { preset_name, values }` — `hasChanges` (changed rows get a `--warn` orange outline / an orange dot in the sidebar) compares key by key against the baseline snapshot when one exists, and against the factory defaults when none does. The baseline is no longer shown as a badge (removed 2026-09, duplicating the "Adjusted" statistic); the "Restore Baseline" (`restoreBaseline`, writing the baseline snapshot back after resetAll) and "Clear Session Params" (`clearSession`, with a confirmation; the model selection is kept) entry points remain on the Params page status bar.
- **Discard protection**: before switching models (`applyModel`) and before applying GGUF suggested parameters (`applyModelWithSuggestions`), `hasChanges` is checked and, when there are unsaved modifications, `confirmDiscardDirty` asks the user to confirm; after confirmation the change is applied and the temporary baseline rebuilt. Re-attaching the previous model at startup goes through `reattachModelRuntime` (direct assignment, no confirmation, baseline not rebuilt, alias not re-derived).
- **`MODEL_KEY` (`model`)** is always carried in the command as `-m`; `set(MODEL_KEY)` derives `alias` automatically (`modelBaseName`, the file name without the `.gguf` extension).

### 5.4 Dependency cascading and speculative-decoding auto-detection (ui/stores/params.ts)

- **Generic dependency cascade cleanup** `syncDependencies()`: it walks every parameter declaring `dependsOn`, and when a dependency is unmet resets the value to its default and presents it as `dep-unmet` (orange outline + background tint + warning icon, see ParamRow; **the control is not actually disabled** — the user can still change the value, and after a change the verdict is recomputed from the current dependency state) — the verdict matches `ParamRow.dependencyMet`: the dependency parameter must be "active" + the value must satisfy values/notValues. **The meaning of "active" is unified with the command builder's `isDependencyMet`**: checkbox dependency sources are judged as booleans (checked means active, so `cache_prompt`, whose default is true, is judged correctly instead of being misread as unmet because "value = default"), all other types are judged by "value ≠ default" (default value = not enabled); **exception**: `file` / `dir` types keep the path the user selected and are not reset (so a long path entry is not wiped by mistake). It is triggered only when the modified key is a dependency source (`DEP_SOURCE_KEYS`), so that "fill the downstream value first, pick the dependency source afterwards" is not wiped by mistake.
- **Dependency groups**:
  - `spec_draft_model` / `spec_draft_ngl` / `spec_cache_type_k/v` → depend on `spec_type` being an external draft type (`draft-simple`/`draft-eagle3`/`draft-dflash`/`draft-dspark`)
  - `spec_draft_n_max` / `n_min` → depend on `spec_type` being non-empty and not `none` (applies to MTP/ngram as well)
  - `reasoning_effort` / `reasoning_budget` / `reasoning_format` / `reasoning_budget_message` → depend on `reasoning` not being `off`
  - `cache_reuse` → depends on `cache_prompt` being `true`
- **Speculative-decoding draft-count cascade** `set('spec_type', ...)`: choosing a speculative-sampling type automatically applies that type's recommended maximum draft count (`spec_draft_n_max`, mapping `SPEC_DRAFT_N_MAX_BY_TYPE`: draft-simple/eagle3/dspark=8, draft-dflash=15, draft-mtp=5, ngram-*=5) and enables it — picking the type without configuring the draft count cannot reach that method's best efficiency; at the same time `n_min ≤ n_max` is preserved (clamping `n_min` when the type changes or when `n_max` is lowered manually). When turned off (none/empty), `syncDependencies` **resets the draft counts to their default values** (`spec_draft_n_max` default **3**, not cleared to 0/empty — `resetDep` assigns `p.default`, see stores/params.ts:337).
- **DFlash / draft-model auto-detection** `detectDraftModel()`: on a model switch it looks for dflash/draft files in the same directory — a dflash file is configured automatically as `spec_type=draft-dflash` + `flash_attn=on` + `spec_draft_n_max=15` (Muse-Glimmer DFlash predicts 16 positions per block: 1 conditioning position + 15 draft tokens); an ordinary draft file sets `draft-simple`; a type already chosen by the user is respected and not overwritten.
- **Automatic re-detection when switching back to an external draft type**: `set('spec_type', ...)` detects that the new value is an external draft type and that `spec_draft_model` is empty, and then calls `detectDraftModel` again to fill the path; when the path already has a value, detection is not repeated. Note: when the dependency is unmet, `file` types **keep the path and are not reset** (see the exception above, only `buildCommand` skips emitting them), so "switch to draft-mtp/ngram and back" normally still has the path and does not trigger re-detection — re-detection happens where the path is empty (after clearing the session / `resetAll`).

### 5.5 Fixed procedure after a binary upgrade (re-pin)

**Background**: the repository pins `docs/params/llama-server-help-out.txt` (the raw `llama-server --help` output) as the baseline of the parameter documentation and as the reference source of the sync checks; `scripts/generate-params-doc.cjs` records the source binary version in the header of `docs/{zh,en}/params/LLAMA_SERVER_PARAMS.md` (both language copies, generated in one run). The app does not ship a bundled binary (the engine directory is chosen by the user), so the pinned help is only a documentation baseline — but after upgrading the engine this procedure must be walked through again, otherwise the parameter table and the docs drift away from the real backend.

**Fixed steps after upgrading the llama.cpp binary**:

1. **Export the new help to a temporary file** (audit first, replace afterwards — if you overwrite the baseline first, the step-3 audit ends up "comparing the new help against the new help", flag additions/removals are always empty and every drift is missed):
   ```
   node -e "const{execFileSync}=require('child_process');const fs=require('fs');const out=execFileSync('.\\llama-bXXX-bin-win-vulkan-x64\\llama-server.exe',['--help'],{encoding:'utf8',maxBuffer:1024*1024*64});fs.writeFileSync('docs/params/llama-server-help-new.txt',out)"
   ```
   ⚠ Do not use PowerShell's `>` redirection: PS5.1 / some environments write **UTF-16** (with BOM / null bytes),
   and the documentation generator reads UTF-8, so it silently parses nothing (hit during the b10734 upgrade; changed to Node spawn + file write on 2026-09-01).
2. **Drift audit** (new help vs pinned baseline: flag additions/removals / default-value changes / app parameters missing):
   ```
   node scripts/verify-help-drift.cjs docs/params/llama-server-help-new.txt
   ```
   Flag-level drift or a missing app flag exits non-zero (CI can block it); default-value changes are only reported and do not fail — whether to follow them is a human decision.
3. **Replace the baseline once the audit passes**: `llama-server-help-new.txt` overwrites `llama-server-help-out.txt`. **Two byte-identical help versions are a legitimate outcome** (b11178 → b11243 was exactly that — the two sides share a sha256), in which case the file does not even diff; step 4 still has to happen, because the UI's "baseline may be outdated" warning compares the **build number**, not the help content.
4. **Update the baseline build number**: the source of truth is the `ENGINE_BASELINE_BUILD` constant in `packages/shared/src/params/engine-baseline.ts`, and **six declaration sites** must follow it: the "当前固定 bN" note in that file's header comment, the two source lines (zh and en) in `scripts/generate-params-doc.cjs`, "基线对齐 llama.cpp **bN**" in `README.md`, "baseline aligned to llama.cpp **bN**" in `README.en.md`, and the parenthetical on the first line of the "current measurement" paragraph in this document in both languages. `verify-params-sync` ⑥ parses each of the six and requires equality (**unparseable also fails**), so missing one turns red. Earlier editions of this document said only "change the hard-coded version string in the generator" — that predates the constant, and following it today updates just 1 of 6.
5. **Check fixtures and mocks that hard-code the baseline value**: anywhere a single literal expresses both "measured data" and "current configuration" is guaranteed to fail spuriously or warn falsely once the constant changes — both consequences were hit, in the real-machine `build_info` inside `packages/core/tests/props-check.test.ts` and in the props-ok demo value of `packages/ui/src/dev/demo-mock.ts`. The rule to apply: keep the captured real-machine string verbatim (it genuinely predates the new baseline, so assert the drift honestly), and derive assertions of the "engine equals the baseline ⇒ no drift" kind from `ENGINE_BASELINE_BUILD` instead.
6. **Update `packages/shared/src/params/definitions.ts`**: add/remove parameters per the audit result, sync the dropdown `options` (allowed values), adjust default values (a default-value change must be decided together with measured conclusions — e.g. when b10429 changed the `--load-mode` default to `auto`, the app kept `none` based on the measurement in `docs/archive/experiments/plan-kv-split-cli-test.md`).
7. **Rebuild shared**: `pnpm --filter @llama-launcher/shared build` (the core tests depend on `dist`, and skipping the rebuild makes tests inconsistent).
8. **Regenerate the parameter documentation**: `node scripts/generate-params-doc.cjs`.
9. **Verify consistency**: `pnpm lint` includes `verify-params-sync.cjs` (six classes of checks, **any discrepancy fails**): ① a three-way cross-check between the parameter definitions ↔ the reference table ↔ the help output; ② the parameter count claims in the documentation (total and per-group) versus measurement; ③ the `PARAM_LABELS`/`PARAM_HELP` key sets must be exactly equal to `PARAMS` in both directions and non-empty for zh/en (in the table but not in the dictionary → the UI renders a bare key; in the dictionary but not in the table → a dead entry); ④ `engineDefault` in `engine-baseline.ts` versus the `(default: X)` in help (key sets equal in both directions, any `default ≠ engineDefault` override must carry a `note`, and an entry that cannot be parsed also fails); ⑤ a single argv emission implementation (only `shared/src/params/command.ts` may assemble it); ⑥ the baseline build number across its six declaration sites. Running the script on its own shows the per-item output.
10. **If IPC channels changed**: sync `packages/shared/src/types/ipc.ts` and the generated preload, then run `pnpm lint` (which includes `verify-ipc-sync.cjs`).
11. **Regression**: `pnpm lint` + `pnpm test`.
12. **Record it**: add entries to the [Unreleased] section of `docs/CHANGELOG.md`.

**Measured reference (2026-09-01, b10502→b10734)**: the flag-level drift audit found **0 removals and 0 missing app flags** (everything at the safety ceiling); writing `--help` to disk moved to Node spawn (fixing the PowerShell UTF-16 redirection trap, see step 1); 9 new parameters entered the table (parameter table 49 → **58**, including `--lazy-mode`, `-ncffn`, `--kv-unified-per-slot`, `-mmdev`, `--video-fps` and others). **Measured reference (2026-09-04, b10734 baseline)**: `verify-params-sync` 67 code flags / consistent with the reference table; `verify-help-drift` found the baseline help's 428 flags all matching (nothing added, nothing removed).

**Reference measurement (2026-09-19, b11053 baseline, version 0.4.1-dev / commit 1af554f8f)**: flag-level drift = **2 additions** (`--log-jsonl` / `--no-log-jsonl`), **7 removals** (`--mlock`, `--mmap`/`--no-mmap`, `-dio`/`--direct-io`/`-ndio`/`--no-direct-io` — all of them standalone aliases already marked `DEPRECATED in favor of --load-mode` back in b10734, and the app had long since migrated to the `--load-mode` dropdown, so **zero impact**); among the 69 flags used by the app **0 are missing**. Default-value changes contained exactly one real semantic change: `--reasoning-preserve` went from `template default` → `enabled` (that flag is not in the parameter table, so no follow-up action). The enum allow-lists were checked item by item with **no drift**: `--load-mode` still includes `dio`, `--spec-type` has all 11 values identical, and the built-in `--chat-template` list is **byte-for-byte identical** to b10734 (our 24 entries are a subset of it). `--log-jsonl` was **deliberately not adopted**: it turns stdout into one JSON object per line, which directly breaks `launcher.ts`'s listening detection (line-based matching of `listening` + `http|server`) and the console's per-line colouring — the same class as `--log-file`. Also fixed one false positive in the `verify-help-drift` parser: a description continuation `… default: follows --device)` does not start with `(`, and the stripping character set does not include parentheses, so `--device)` was treated as a new flag (the very first run of this pass reported a bogus "added --device)"); after the fix the flag counts of both sides dropped in step — **the b10734 baseline went 428 → 421, and the current b11053 baseline measures 416** (self-comparison outputs `baseline flags: 416 | new flags: 416`; whenever quoting these numbers always state "which baseline + which parser version").

**Reference measurement (2026-09-26, b11178 baseline, version 0.5.0-dev / commit f9af9be21)**: flag-level drift = **0 additions, 0 removals** (416 ↔ 416, and **0** of the app's 69 flags missing). After re-pinning, `verify-params-sync` still reports "all 49 engine defaults cross-checkable against help are identical", i.e. **not one app parameter changed its engine default between these two versions**, so `definitions.ts` and `engine-baseline.ts` needed no value edits this round. Three real changes are worth recording:

1. **`--host` now accepts comma-separated multiple addresses** (the description adds "with multiple TCP addresses, `::` binds IPv6 only" and "overlapping addresses result in undefined behavior"); the default is still `127.0.0.1`. `verify-help-drift` reported this as a *default-value change*, which is diff noise from `(default:` being wrapped onto the next line — comparing the raw text on both sides confirmed no change (**when the drift script flags a default change, first check whether the line wrapped**). A launcher-side defect was fixed along with it: using the whole string as a single address produced an unopenable URL such as `http://0.0.0.0,::1:8080/`, and the port probe tried to bind a non-bindable string, reporting an occupied port as free. Parsing now lives in shared as `hostList` / `tcpHosts` / `displayHost` (see `ServerInfo.url` in [data-persistence.md](data-persistence.md) and `system:checkPort` in [desktop-main.md](desktop-main.md)).
2. **The `(env: LLAMA_ARG_*)` channel grew from 139 to 145 entries**, and the 6 additions are exactly the sampling family (`LLAMA_ARG_TEMPERATURE` / `TOP_P` / `MIN_P` / `REPEAT_PENALTY` / `PRESENCE_PENALTY` / `FREQUENCY_PENALTY`). **57 of the 60** app parameters now carry such a channel. This opens a new gap in the emission premise: "value equals the engine default ⇒ do not emit" is only sound when **nothing else rewrites that default**, and these variables are precisely something else. Measured on b11178 (malformed env value alongside a valid command-line argument): env is processed during startup and **aborts the process even when the command line passes a valid value**. Handling is documented in item 24 of [design-decisions.md](design-decisions.md) and via `ServerInfo.envOverrides`.
3. **`--completion-bash` cannot serve as a default source**: measured output is 298 long flags crammed onto one line, with neither types nor defaults; `--list-devices` yields devices only, and `--json-schema` / `-jf` are for constrained generation, not configuration export.

**Reference measurement (2026-09-29, b11243 baseline, version 0.5.0-dev / commit fc07d781e)**: one-sentence conclusion for this round — **the new help is byte-for-byte identical to the pinned baseline** (both sides share the same sha256, 59,615 bytes / 732 lines). Hence flag 416 ↔ 416, 0 additions, 0 removals, **0** of the app's 74 flags missing, 0 default-or-description changes, and no value edits in `definitions.ts` or `engine-baseline.ts`. Upstream moved 65 commits from b11178 to b11243 (GitHub compare), changing the implementation rather than the parameter surface. Four judgements worth recording:

1. **Why re-pin at all when drift is zero**: comparing `/props` `build_info` against `ENGINE_BASELINE_BUILD` is the only runtime channel that can catch "measuring a new engine with an old ruler". While the baseline stayed at b11178, every user on b11243 saw a baseline-drift warning on each start — and this byte-identical help proves the two are equivalent. **An alarm that fires falsely all the time gets ignored, which voids the channel.** Re-pinning costs six declaration sites, and `verify-params-sync` ⑥ parses each one and requires equality, so missing one fails.
2. **Two couplings that hardcoded the baseline value were removed along the way**: `packages/core/tests/props-check.test.ts` used the `build_info` literal from the real-machine snapshot to carry two meanings at once — "the genuine read-back shape" and "engine equals baseline, so no drift should be reported" — and the moment the baseline moved the second one failed spuriously. The fixture string is now kept exactly as captured (history stays honest), while the "equal ⇒ no drift" branch builds its value from `ENGINE_BASELINE_BUILD`; the props-ok demo value in `packages/ui/src/dev/demo-mock.ts` does the same, otherwise the mock page shows itself as drifted the instant it opens. **Lesson**: a fixture literal that expresses both "measured data" and "current configuration" is guaranteed to fail spuriously on a re-pin — derive the latter from the constant.
3. **The env channel was re-measured**: help still lists 145 `(env: LLAMA_ARG_*)` entries (same as b11178), but recounting against the current table gives **67 of the app's 74 flags** carrying one. The "57 of 60 parameters" figure in the previous entry was taken when that table had 60 parameters, and is kept verbatim as a historical record rather than silently updated to today's value.
4. **Not verified this round (recorded honestly)**: the `/props` field shape was **not** re-captured from a real b11243 instance — on this machine `models_dir` points at a directory that does not exist and there is no GGUF anywhere, so no server can start. A byte-identical help makes the CLI-side judgement trustworthy, but `/props` is engine-internal: if anyone added or renamed a field across those 65 commits, only a real read-back would show it. To close this, run `node scripts/verify-server-start.mjs --model=…` in an environment that has a model, or GET `/props` directly and diff it against the fixture above.

**Current measurement (2026-10-06, b11408 baseline, version 0.5.0-dev / commit 9f12cd4a4)**: local `llama-b11408-bin-win-vulkan-x64` (build number +165 over the previous baseline; upstream commits not enumerated). The help surface gains exactly one flag — `--spec-draft-sampling` (`{greedy,probabilistic}`, default `greedy`, with the `LLAMA_ARG_SPEC_DRAFT_SAMPLING` env channel and no short alias); `verify-help-drift` reports flags **416 → 417, 0 removals, 0 missing** among the app's 74 flags, and the whole-file diff of the two help texts is precisely those 5 added lines with **0 rewritten lines**. Three judgements worth recording:

1. **The parameter table is untouched this round**: the new flag is not adopted, `definitions.ts` and `engine-baseline.ts` keep their values, so the reference table gains one "⬜ not supported" row while the parameter total stays 64. Adopting it is a separate account (13 count declarations plus a new baseline key) and is decided separately from re-pinning. `(env: LLAMA_ARG_*)` in the help goes from 145 to 146 entries and that flag is the entire difference; "67 of the 74 app flags carry that channel" is unchanged (the new flag is not in the app table).
2. **The drift notice becomes directional (the behavioural change of this round)**: `driftOf` used to fire whenever the build numbers differed. Once the baseline is pinned to the newest version, that hits every user who upgraded their engine ahead of us, whereas the people who genuinely need the warning are those on an engine **older than the baseline** — for them the default basis of the non-readable parameters may not line up. It now only speaks when `engine < baseline`, and both language strings were reworded to "Engine build is older than the parameter baseline". **The cost has to be stated**: users on an engine newer than the baseline now get **no warning at all**, so "upstream moved and we have not re-pinned" is back to being covered only by the re-pin discipline and this section's procedure, not by a runtime channel.
