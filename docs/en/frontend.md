### 7.1 Routing and feature registry (router/index.ts + features/)

Routing is assembled from a **feature registry**: every feature module under `packages/ui/src/features/` declares a `FeatureDef` (`nav` sidebar entry + `routes`), and `features/index.ts` aggregates them into `navItems` (rendered by the sidebar) and `featureRoutes` (assembled into the router); `router/index.ts` is nothing but `createWebHashHistory` + `featureRoutes`. Adding a feature = adding one entry to the registry; `enabled:false` turns it off; `order` decides the sidebar sequence; the orange dot on the Params page is evaluated inside the render context through `nav.dot()` so that it stays reactive. **The sidebar sub-tree has been removed** (2026-09: `children[]` and the expand mechanism went away when "Params" came back to a single page) — secondary pages all return to **in-page tab-strip switching** (the two tabs of "Params" use the same idiom as the Settings page, deep-linkable through `query.tab`); the "has adjustments" dot is rendered as a **badge on the top-right of the icon** (visible with the sidebar collapsed, not clipped by the 48px rail's overflow), and every nav button carries `title`/`aria-label`. **Startup order** (main.ts): `settings.load()` and the `last_tab` tab restore finish **before** `app.mount()` — the very first frame already shows the target tab, so there is no second navigation during startup (restoring after mount injects a navigation in the middle of the first paint, which looks like the route already switched while the view stays on the old page); settings loading has a **3s timeout fallback** (`Promise.race`, so a failing load enters directly by the current URL instead of blocking startup). **Page switching** (PageHost) is a **structural direct replacement**: `keep-alive` swaps the activated component directly (structurally there is no window in which two pages are on screen together), and after the route `watch` the content area gets a `--dur-fast`(0.16s) container fade-in (**CSS keyframes**, opacity 0.55→1, replayed by alternating two same-shaped keyframe classes `is-fade-a` / `is-fade-b`; the first frame is `null` and does not fade); reduced-motion is no longer decided by a one-shot `matchMedia` snapshot on the JS side but turned off by the global rule in `reset.scss` (the old JS leg read a setup-time snapshot, so changing the OS preference mid-session had no effect). The previous implementation was a 90ms WAAPI `el.animate(...)`, folded into CSS on 2026-10-07 to remove the second motion mechanism; **`<transition>` is not used** — given KeepAlive's deactivation/removal timing the JS hook `done()`/`transitionend` may never fire, producing a brief frame with two pages on screen during fast navigation (the old approach is deprecated, see STYLE_TODO #40). **Browser preview** (environments without the Electron preload): `main.ts` injects the `createDemoApi()` demo data from `dev/demo-mock.ts`, in which the command preview calls `buildArgv` from `shared/params/command.ts` (the very same emission implementation as a real launch — see [core-modules.md](core-modules.md) §4.3; the mock used to ship its own simplified command builder that drifted every time the emission rule changed, removed on 2026-09-26, regression case in `src/dev/demo-mock.test.ts` per [testing.md](testing.md)); that injection uses **`await import()` dynamic loading** (finished before `app.mount()`, so the first frame has complete data) — a static import would push the demo data into the 244 kB entry chunk, and every Electron launch would pay to read and evaluate a copy of code that is never used.

**Resource-cleanup rules under keep-alive (2026-09-19 performance review)**: `PageHost`'s `<keep-alive>` means components are **not unmounted** when you switch pages, so cleanup written in `onUnmounted` **never runs** — timers, `window.addEventListener` and `window.api.*.onXxx()` subscriptions must be paired in `onActivated` / `onDeactivated` (historical defects: the Settings page's non-passive capture-phase `scroll` listener, the Models page's 2.5s health-check poll and its `models:onChanged` whole-tree-rescan subscription — visiting the page once kept them resident for the lifetime of the app — and the health-check poll among them was removed outright on 2026-09-26 in favour of a main-process push, so it is no longer "a poll that gets cleaned up properly" but "a poll that should never have existed"). For the same reason, page-level costs that "recompute for every row" keep running after deactivation: forced-layout work such as console auto-scroll must be gated by `pageActive` and coalesced into a single frame with `requestAnimationFrame` (since 2026-10-07 implemented **in one place**, `composables/useAutoScroll.ts`, consumed by `ConsolePanel` and the Dashboard mini list — before that LogsPage / ServicePage / DashboardPage each carried a copy, and the "near bottom" threshold had forked between 60 and 80, now unified to 60). Derived values of list rows (colouring class names, timestamp formatting, quantization parsing) should be computed once **when the data is enqueued** and carried with the entry (`server` store's `OutputLine.tone/oom/time`, `appLog` store's `AppLogLine.time/cls/lower`), never recomputed row by row inside a `v-for` function call. **A sub-tab toggled with `v-if` is not the same thing as a route switch** (2026-10-06): what `PageHost`'s keep-alive preserves is the *page*, so a sub-panel the page toggles with `v-if` is still destroyed and recreated and every component-local ref goes with it (observed cause: a health check that takes 1–3 minutes finishes, you switch to the Model Library tab and back, and the badge is gone). The local-models panel is now wrapped in `<KeepAlive>`, the same pattern the params page uses for `PresetsPanel`.

**Same-rule extension (2026-10-06)**: caching `v-if` sub-panels was extended to two more places — the Model Library (the `DownloadCard`'s URL parse result, search results and file checkboxes were all empty after a round trip) and Settings → General (engine detection runs "on mount": a 400 ms debounce plus two IPC round trips and a directory scan, so every time you switch back the badge first drops to the grey "not detected" and only then jumps back to "ready"). `LibraryPanel` is now cached as well, on a premise that was checked rather than assumed: its subscription goes through `download.ensureSubscribed()`, an idempotent entry point, not the "subscribe on mount, unsubscribe on unmount" shape — so last round's reason for excluding it turned out not to hold. **Scroll position is a different class of loss (located, not fixed this round)**: `.app-content` is the shared scroll container for the params/logs pages (measured `scrollHeight 3917 / clientHeight 705`), and keep-alive preserves the component but not `scrollTop`, so coming back always lands at the top. A per-`route.fullPath` save with a render-frame restore was attempted and **failed twice in the browser** (the page swap waits for the router to resolve and re-render, so at assignment time the container has not grown back and the value clamps to 0; retrying per frame did not rescue it either) and was reverted rather than shipped as a mechanism that looks fixed but is not. Fixing it properly requires establishing the real content-height sequence around the page swap — the 90 ms container fade-in in `PageHost` versus keep-alive activation — before writing any restore code.

**Two points where the criteria were unified (2026-10-06)**: (1) "can the built-in Web UI be opened right now" now lives in one place, `server.canOpenWeb` (i.e. `status === 'running'`), shared by the top-bar button, the overview card button and the embedded frame — previously the top bar was clickable during `starting`, and jumping there showed "service not running". (2) The console's "new logs" pill is now **absolutely positioned inside the log box, bottom-right** (changed on both the service page and the logs page — no exceptions left behind): it used to sit in normal flow above the box, so appearing at all pushed the whole block down one notch, which is the "box height jumps" the user saw. (3) With the `stopping` state in place, the two previously unreachable "stopping" branches in `StatusBar` / `ServiceStatusCard` became live code, and `StatusBar` no longer labels the stop sequence with the `status_starting` string (it uses `svc_status_stopping` now).

### 7.2 Stores (6 Pinia stores)

| Store | Responsibility |
|-------|------|
| `settings.ts` | Load/save settings (200ms debounce + `flushSave` forced write), theme switching (`data-theme`, including `system`, which follows `prefers-color-scheme`), language switching |
| `i18n.ts` | Uses `settings.language` as its data source, synced with `watchEffect` |
| `params.ts` | **Dual-track parameter logic**: the `values` value map + `baseline` (`SessionBaseline { preset_name, values }`) — the session track writes `session_values`/`session_baseline` into settings.json through `persistSession` with throttling (autoSave watch, 800ms throttle, **never writes preset files**), and restores the last session at startup via `restoreSession`; the preset track is written only on an explicit save. `hasChanges` compares key by key against the baseline snapshot when a baseline exists (against the factory defaults when it does not); `markBaseline`/`restoreBaseline`/`clearSession` manage the session; switching models or applying GGUF suggestions (`applyModel`/`applyModelWithSuggestions`) first goes through `confirmDiscardDirty` so unsaved work cannot be lost silently, while re-attaching the model at startup goes through `reattachModelRuntime` (no confirmation, baseline untouched); `set(MODEL_KEY)` derives `alias` automatically (`modelBaseName`); dependency cascade cleanup (`syncDependencies`) + draft-model auto-detection |
| `server.ts` | status/pid/host/port/url, `stopInfo` (the stop fact pushed by the main process — the only input for the failed/crashed states; log text never decides whether the process is alive), `readyAt` (this round's readiness moment pushed by the core, still set during `stopping` — "uptime" is derived from it; a renderer-recorded start would show "—" or run short on first page entry / reload), `apiUrl` (**the single source of the API address**, see §7.5.7), `runningValues` (snapshot of the parameters of the most recent launch), output array (cap 5000) |
| `download.ts` | Task list, IPC listener registration (`ensureSubscribed` registers only once) |
| `appLog.ts` | Application log buffer (consumes `logs:*` IPC pushes, rendered by the Overview page's application-log window — before option B it was consumed by the Logs page) |

**The relief-advice row for "it does not fit"** (params-system §5.6, item 3): the overview status card's `.oom-row` offers advice **before** the server is even started (at most two buttons, each writing a parameter via `params.set`; an entry already at that value never appears). Four rules: ① it is a **statically reserved permanent slot** (`visibility: hidden` + `min-height`), so speaking and staying silent never change the card height (guarded by `e2e/web/offload-advice.spec.ts`: equal heights and the tier rules in both languages, an untruncated English sentence, plus four "remove the reservation / remove the marker and it must turn red" self-proving legs); ② "it does not fit ⇒ change which parameter" is **decided in exactly one place**, core's `recommendOffloadAdvice`, whose entries carry an `offloadRelief` marker and ride the existing `system:estimateVram` channel, while `stores/hardware.ts` only converts units and splits by that marker — recomputing it here would be a second implementation; ③ with no devices detected or no entries emitted **not a single line appears**: the UI never dresses "not measured" up as "fine"; ④ while the service is running the advice row stays silent (shouting "it does not fit" at an already-loaded model contradicts itself), and a real OOM is handled by the existing stop-fact attribution. Fetch timing follows §7.1's first iron rule: `hw.enter()` is called in `onActivated` and returns an idempotent release, `onDeactivated` releases it, and a background page never knocks the main process. **The "where the weights went and why it is slow" sentence is deliberately not on this page**: the service page used to carry a second copy, which duplicated the Params page status bar's "VRAM occupancy (estimated)" stat, so it was removed on 2026-10-06 by user request and merged into that stat's tooltip (`msg_occ_spill_line`, shown only when some weight really sits in RAM) — the Params page is the single home for that sentence.

### 7.5 Styling system (Arco Design Vue)

> `@arco-design/web-vue` is the single component and design-token foundation of the UI. The theme is written by `stores/settings.ts` into both `html[data-theme]` and `body[arco-theme]`; the legacy `--*` variables exist only as a compatibility layer for business components that have not finished migrating, and must not be used in new UI.
>
> New UI must prefer Arco's `Button`, `Form`, `Input`, `Select`, `Modal`, `Table`, `Tooltip`, `Tag` components and their CSS Variables. Glassmorphism, the hand-written button system and custom overlays are no longer loaded; the legacy rules below are reference material only while the remaining business components finish migrating.

**How components are imported (2026-09 on-demand import)**: components are resolved on demand on the vite side by `unplugin-vue-components` + `ArcoResolver` (`importStyle: 'css'`) (the Components plugin in `vite.config.ts` has `dirs: []` — auto-registering local components is forbidden) — adding an Arco component needs **no explicit import**, and the template `<a-*>` tags plus their styles are bundled on demand; `src/components.d.ts` is the **global component declaration** generated by the plugin (committed, and `vue-tsc` type-checks against it), so after removing components or dependencies you must verify it was updated in step. `main.ts` has dropped `app.use(ArcoVue)` and the full `arco.css`, keeping only the global base CSS (`@arco-design/web-vue/es/style/index.css`) so that the theme variables stay available.

#### 7.5.1 Design tokens (`packages/ui/src/styles/`)

> State after the completed 2026-09 migration: `theme.scss` keeps only **Electron layout dimensions, business semantic colours and the migration compatibility layer**; everything else references Arco's CSS Variables directly (`--color-text-*` / `--color-fill-*` / `--color-bg-*` / `--color-border-*` / `rgb(var(--primary-6))` / `rgb(var(--success-6))` etc.). The old business palette (`--accent`, `--bg-*`, `--shadow-modal/tooltip`, `--overlay`, …) has been deleted entirely and must not be referenced again; **the only name family brought back is `--fg-*`, and it is not the old palette resurrected** — measurements on 2026-10-07 showed that "just use Arco's semantic colours for text" does not clear this repository's own 4.5:1 bar, so a "text role tier" layer was added to make that decidable (see the 文字角色色档 / text-role colour entry below).

- **Accent colour**: Arco's primary `rgb(var(--primary-6))` (pure blue). Interaction emphasis (outlined buttons, focus borders, selected rows, active tab) always uses it; hover/selected states use the Arco component's own state or `--color-fill-3`.
- **Business colour tokens** (`theme.scss`, not switched by theme): `--btn-h`(30) / `--fs-appname`(16) / `--statusbar-blue`(#007acc) / `--badge-cat-*`, `--badge-quant-*` (download-category / quantization badge palettes; the source badge claims no hue and stays neutral with `--color-text-2` + `--color-fill-2`, see §7.5.7) / `--console-bg`(#1d2129), `--console-fg`(#e5e6eb) (console / command preview keep a constant dark background, unchanged in both themes) / `--primary-fg`(#fff, text on a solid primary background).
- **Selected-row background** `--row-selected-bg` (`theme.scss`, theme-switching since 2026-09-13): light = `rgb(var(--primary-1))`; dark = `rgba(var(--primary-6), 0.2)`, a translucent blue tint — in dark theme `primary-1` is a near-black navy darker than the page background, so flooding a whole row looks far too heavy, hence no dark colour block is used there. Three selected states reference the same token: the selected model-table row (including the keep-the-colour-on-hover rule), DownloadCard `.active`/`.checked`, FileBrowserModal `.is-selected`.
- **Compatibility-layer mapping** (until the migration is complete): `--radius-pill/row/control: 4px`, `--fs-xs/sm: 12px`, `--fs-base: 13px`, `--fs-md/lg: 14px`, `--ease-smooth: ease`, `--dur-fast: 0.16s`. The three radius names are now only semantic aliases whose value is the Arco tier `var(--border-radius-medium)` (4px); Arco exposes no font-size CSS variables (components hardcode px), so `--fs-*` stays ours. Deleted for having zero consumers: `--dur-med`, `--ease-jelly`, `--shadow-dropdown`, `--z-overlay`. Business components may consume only these names, or use Arco variables directly; new code prefers Arco variables.
- **Text-role colour tiers** (`--fg-*`, declared on `body` so they can read Arco's palette, theme-switching): `--fg-hint` / `--fg-accent` / `--fg-warning-text` / `--fg-danger-text`. **They exist because measurement disproved "Arco's semantic colours are good enough as text"**: `--color-text-3` on white is only **3.24:1** and on `--color-fill-2` only **2.92:1** (Arco designed that tier for placeholders and disabled states), and the state colours as text give warning **2.57** and danger **3.71**. After re-tiering, measured values are hint 7.10 (light) / 15.7 (dark), accent 5.19 / 5.98, warning-text 6.05 / 7.21, danger-text 5.43 / 5.36 — all ≥4.5. **Hierarchy is carried by font size, weight and letter case; colour carries legibility only** — this is the fundamental difference from the old "palette equals hierarchy" system. `--color-text-3` is demoted to decorative glyphs (the `=` separator inside chips) and placeholders, and must not carry information. **Two traps in the same family**: (1) Arco's `.arco-btn-text` ships `color: rgb(var(--primary-6))` (measured: it is the only colour rule matching a text button), i.e. **every text button in the app is accent-blue** — 5.19 on light (clears) but only 4.2 on dark, so `theme.scss` now points them at `--fg-accent` (unchanged on light, 5.98 on dark); the status bar is an unchanging blue chrome, so text buttons there must keep `color: inherit` or this rule drags them off white (an actual regression measured once: 14 nodes fell from 4.51 to 2.7). (2) To change the label of an `a-tag` preset pair the selector must be `body .arco-tag.arco-tag-checked.arco-tag-<colour>` — Arco uses a three-class selector, so losing one class (even just adding `body` for two classes plus an element) loses, and component CSS is injected at runtime after this file (the same cause as the tab-gap incident in §7.5.6). The constant dark surface has its own tier `--console-accent` (stored as a triplet, consumed as `rgb(var(--console-accent))`, 6.26 on `#1d2129`) and the green-label tier `--fg-on-tag-success` (4.84 on light, Arco's own value on dark); **both are pinned literals**, for the same reason as `--log-kind-*`. Re-measured across the app: 152 visible text nodes in the dark theme with **0** shortfalls, 433 in the light theme with 15 left, **all** of them the registered decorative `=`.
- **Change the variables Arco reads, not the declarations Arco writes** (redone on 2026-10-07 after the user's "do not prefer custom styles, prefer Arco native"). Measured: Arco takes its colours from variables — filled buttons use `bg=rgb(var(--warning-6))` / hover `--warning-5` / active `--warning-7`, **outline buttons use the same family as their text colour**, tags use `rgb(var(--green-6))`, text buttons and the selected menu item use `rgb(var(--primary-6))`. Stepping a variable therefore covers both forms and every state in one move, while Arco keeps computing hover / active / loading / disabled itself; overriding declarations needs one rule per state plus a fight with specificity and runtime injection order (that was the previous version: 8 rules and 6 tokens, all now deleted). Light steps `--warning-6/5/7`, `--danger-6/5/7` and `--green-6` on `body` (measured 4.84-14.26 on white and on the matching pale surfaces, where Arco's own values gave 2.57 / 2.63 / 3.71); dark raises the tier **inside four scopes only** (filled buttons `--primary-6: 29,77,210` with white = 6.90 and hover `--primary-5: 14,50,166` = 10.37, because Arco's bright dark-theme primary gives white labels only 3.74; text buttons, sidebar and blue tags rise to primary-7 = 5.98). **Overriding the global `--primary-6` is deliberately avoided**: 66 elements resolve to that exact colour in the dark theme, so stepping it swaps the whole accent system for one defect. Measured after the change, all six button states pass — light 5.19 / 7.70 / 5.19 and dark 6.90 / 10.37 / 6.90 (rest / hover / focus) — with **zero property overrides**. **(This bullet documents the technique and still governs the dark scoped steps; light was reverted to zero steps the same day — see the "Light theme now carries zero palette steps" bullet, and the light figures quoted here are kept as a historical measurement.)**
- **Even a "text colour only" override is forbidden** (added measurement, 2026-10-07): a compiled scoped rule carries a `[data-v-*]` attribute, so its specificity is (0,4,0) — higher than Arco's `.arco-btn-outline.arco-btn-status-danger:hover` at (0,3,0). Overriding `color` therefore **also freezes the hover / active text colour**: measured on hover the border takes `--danger-5` = `rgb(161,21,30)` while the text stays at the base `rgb(203,39,45)`, so the two directions diverge and the state feedback is wrong (same shape in both themes). All 10 such overrides are deleted (top-bar Stop / Restart / Open Web UI, the Clear-console buttons on the Logs and Service pages, the inline delete buttons on the Models and Presets panels, the download task Cancel, the trash scan button, the About-page links); after deletion, rest and hover measure text = border (light 203,39,45 → 161,21,30, dark 247,105,101 → 245,78,78) while the default colour is unchanged to the pixel — those overrides were restating values Arco already produces after the tier steps. Gate 18 now holds this: any `color` / `background` / `border` declaration on an `a-button` must be registered with a reason in `BTN_COLOR_ALLOW` (four accepted families, 8 rules: win-btn window chrome, the constant-dark console pill, the status bar's `color: inherit`, the muted help icon), and the registry also checks the expected rule count.

- **Light theme now carries zero palette steps: state colours use Arco's official tiers** (reverted on 2026-10-07 after the user's "in light mode the look clearly does not match the Arco library" plus "use official best practice completely"). Arco's state colours are an **indirection** — `--danger-6: var(--red-6)`, `--warning-6: var(--orange-6)` (`es/style/color/css-variables.less`) — and components read those `-6` slots, so stepping them on `body` repaints far more than buttons: alert, form validation text, tag, badge, progress, switch, steps and result all follow (measured: 125 elements affected in light). The companion measurement: **those light steps never applied in dark** — Arco's `body[arco-theme='dark']` (0,1,1) outranks our `body` (0,0,1), so the previous state was the asymmetric "light repainted, dark native", which is exactly why dark looked acceptable and light did not. Text that carries information still has to clear AA, and does so by pointing `--fg-*` **straight at a deeper tier of Arco's own palette**: light `--fg-danger-text = rgb(var(--red-7))` (5.43 on white) and `--fg-warning-text = rgb(var(--orange-8))` (6.05 on white); dark keeps the semantic `-6` slots because the dark tiers are already bright enough. **A palette tier is public vocabulary; a `-6` slot is the library's semantic assembly point — choosing the former is picking a colour, changing the latter is changing the library.** Four dark scoped steps are kept (filled primary → primary-4 with hover primary-3, text buttons and sidebar → `--primary-6: 104,159,255`, blue tags → `--arcoblue-6`), which is the part the user explicitly called acceptable.

- **Colours on the constant dark surface must be pinned literals**: `--log-kind-info`, `--log-kind-error`, `--log-kind-warn` and `--log-kind-success` hold literal `rgb(...)` values and **not** `rgb(var(--arcoblue-4))`. Arco's palette variables flip whole tiers under the dark theme (measured: `--arcoblue-4` goes from 106,161,255 to 29,77,210), which drops the contrast on the same `#1d2129` surface to **2.34** — worse than the 4.32 before the change. "The surface never changes, so neither may the colour" cannot be expressed with `var()`; the status-bar coloured chips (§7.5.7) follow the same rule.
- **Motion and elevation scales**: two durations — `--dur-fast` (0.16s, interaction feedback) and `--dur-ambient` (2s, ambient hints such as the "new logs" pulse in §7.5.6) — and two layers — `--z-chrome` (2, in-page persistent decoration) and `--z-raised` (20, a frame covering content). Bare values are replaced by these tiers; `--dur-med` and `--z-overlay` were deleted for having zero consumers — once overlays moved onto Arco components the library issues the stacking order itself (§7.5.6).
- **Fonts**: body text uses Arco's default stack; `--font-mono` = `'Cascadia Code', 'Cascadia Mono', Consolas, monospace`, and numbers / paths / commands are always mono.
- **Font sizes** (semantic, bare px forbidden): `--fs-xs`(12 badges / auxiliary) / `--fs-sm`(12 secondary hints / status bar / chip) / `--fs-base`(13 body / input / console) / `--fs-md`(14 buttons / list items) / `--fs-lg`(14 card titles / parameter names) / `--fs-appname`(16 app name).
- **Layout metrics**: `--topbar-h`(52) / `--sidebar-w`(224) / `--sidebar-w-collapsed`(48, matching Arco sider/a-menu's default collapsed width — do not change it to 64) / `--statusbar-h`(28) / `--btn-h`(30).
- **Overlays**: shadow, scrim, stacking and entry animation all come from the Arco component defaults (popups, dropdowns and popovers ship their own opaque surface + shadow); the business side has no self-built overlay left, so `--shadow-dropdown` was deleted.
- **Hardcoding ban**: no bare colour values / bare font sizes / bare spacing / bare shadows / bare numeric radii inside components; colours and shadows must go through `var(--*)`; `#fff` is allowed only as the text colour on a solid primary (primary/semantic) background.

#### 7.5.2 Theming

- The theme is written twice: `applyTheme` in `stores/settings.ts` sets both `html[data-theme="dark|light"]` (default light since 2026-09-13; the bootstrap attribute in index.html comes from the same source — dark / follow-system must be selected explicitly under "Settings → Appearance") and `body[arco-theme]`; custom tokens switch on `data-theme`, Arco components switch on `arco-theme` automatically.
- **Base tone (after the 2026-09 flattening)**: backgrounds are always Arco surface colours — `body { background: var(--color-bg-1) }`, surfaces / inputs / overlays use `--color-bg-2/3`, `--color-fill-2/3`; text uses `--color-text-1/2/3`. The old blue-white gradients (`--bg-app-gradient`/`--bg-grad-*`) and the glass layers (`.glass-layer`, `--glass-blur`) were removed along with the completed migration.
- **Contrast**: **Arco's default token system does not itself clear AA** (measured: `--color-text-3` is 3.24 on white and 2.92 on `--color-fill-2`; state colours as text land between 2.57 and 3.71), so any text that carries information must use the role tiers from §7.5.1 (`--fg-*`), leaving `--color-text-3` to decorative glyphs and placeholders; the only business exceptions are the console / command preview (constant dark `--console-bg` + `--console-fg`, with level colours pinned as literals in `--log-kind-*`). **Text is never dimmed with `opacity`**. The previously registered "white label on a filled `--primary-6` = 3.74 in dark" is now resolved by stepping the variable Arco reads in §7.5.1 (measured 6.90 / 10.37 / 6.90 for rest / hover / focus), leaving three permitted classes of shortfall, each with a stated reason: (1) the `=` separator inside chips keeps `--color-text-3` (purely decorative — the information is carried by the key and value segments); (2) disabled labels are exempt under WCAG, and disabled surfaces/labels are left to Arco's own greying rather than re-tuned by us; (3) **the component preset tiers the library itself computes** do not clear 4.5 as light-mode text, and are deliberately left alone because "matching the design-system library" wins here (user decision, 2026-10-07; measured per family): outline danger button text `red-6` = 3.71 on white, 3.25 on a `red-1` surface, 3.01 on hover (`red-5`); outline warning button `orange-6` = 2.57 on white; green `a-tag` text `green-6` on `green-1` = 2.63; the filled primary button measures 5.19 at rest (`arcoblue-6` + white, passing) and 3.65 on hover (`arcoblue-5` + white, not passing). **The boundary of this class is "only colours the library computes"**: any text we write must still use the `--fg-*` role tiers — measured `--fg-hint` 7.10 / `--fg-accent` 5.19 / `--fg-danger-text` 5.43 / `--fg-warning-text` 6.05, including the engine status badge on a translucent surface (`red-7` over a 14% `red-6` blend) at 4.51, all passing.

#### 7.5.3 Radius system (2026-09 flattening: 4px app-wide, aligned with Arco)

- The radius tokens have been flattened to a single value: `--radius-pill` / `--radius-row` / `--radius-control` are all **4px** (the migration compatibility layer, equal to Arco's default radius). Bare numeric radii are forbidden inside components.
- Component radii come from the Arco component default (input / select 2px, **a-tag 2px** (`--border-radius-small`), buttons 4px etc.) — do not write overrides to "restore the old look"; the **exception** is filter chips and coloured small badges, which by business convention explicitly take `--radius-pill` (4px, filter-label / badge semantics, see §7.5.4 ① and §7.5.7); DownloadCard's `.cat-chip` and `.source-badge` / `.quant-badge` / `.file-cat` / `.rec-badge` all belong to that group.
- **Exceptions (exactly two)**: `2px` for the slider track; `50%` for circles (status dot, switch knob, slider thumb, circle icon button).
- **Boundary**: multi-line text containers (command preview `a-textarea` etc.) use `--radius-row` (4px) for their radius, pill shapes forbidden; sticky table headers use an opaque background (`--color-bg-2`).

#### 7.5.4 Spacing rules

- **Page**: `padding: 20px 24px 24px` (inlined in `PageFrame.vue`; `variables.scss` was deleted along with the migration); **section style** — `page-frame` and each page's `.tab-content` use a vertical `gap: 0`, with adjacent content blocks separated by solid rules (the Card's bottom border line, Dashboard's `.q-section + .q-section` top border line); inside a block, `gap: 10px` is the default spacing between elements.
- **Spacing scale** (gap inside components may use only the values below — audited item by item across the repository, no outliers; the authoritative count is `pnpm style:audit` rule 4, so do not hard-code it in the docs; **there is no 1/2/3px micro-gap tier**, so the pixel-tight inner padding of compact atoms also takes the smallest scale value, 4px):
  | Scale | Semantic use |
  |---|---|
  | `4px` | Compact lists (file list items), status dot and text |
  | `5px` | chip inner text-to-count-badge |
  | `6px` | Card-header actions / dense button groups (cat-filter, tasks-actions) |
  | `8px` | **standard button-group spacing** (page toolbars, inline action areas, §7.5.5) |
  | `10px` | Dialog button groups, status-bar elements, secondary groups inside cards |
  | `12px` | Large groups (download task statistics, Dashboard statistics groups) |
  | `14px` | Inside a card, the distance **from a group divider rule to its content** (`padding-top: 14px` in `DownloadCard` / `DashboardPage`; the spacing between cards is the 16px of the next bullet) |
- **Two hard rules when overriding Arco's default styles (three measured lessons: #65 ① / #68 / #70)**: ① specificity must be **strictly higher than** Arco's counterpart rule — **equal specificity loses**, because component styles are injected at runtime as `<style>` by `unplugin-vue-components` + `ArcoResolver` and therefore land after the bundled CSS (this is why the tab title had been silently broken for a long time: `.arco-tabs .arco-tabs-tab-title` (0,2,0) against Arco's `.arco-tabs-nav-type-line .arco-tabs-tab-title` (0,2,0)); ② `gap` only takes effect on a flex/grid box — when adding `gap` to an Arco element you must also confirm its `display` (declaring it together if necessary). The acceptance test is always "read the computed value on a real machine and measure the geometric gap", not what the CSS appears to say.
- **Icon + text rows**: the gap between an icon and its own text label on the same line is **6px** (in-page tab titles, `SettingsPage .summary-item` and status-bar entries follow the same rule).
- **Unit conventions for numeric components (check the source before wiring up Arco, STYLE_TODO #71)**: `a-progress`'s `percent` is a **0–1 fraction** (`line.js`: `width = percent × 100%`, label text `percent × 100 + '%'`) — passing a percentage pins the bar to full from the very first step and decouples it from the real byte count; `a-slider` takes raw `min`/`max`/`step`; `a-switch`/`a-checkbox` take a boolean `model-value`. `style:audit` rule 13 statically intercepts `:percent` bindings (anything containing `100` / `Pct` is ❌).
- **Spacing between a top strip and its neighbouring block** (unified 2026-08-29): the bar-shaped containers at the top of a page (tab-strip, status-summary, toolbar, params-status-bar, status-bar, stats-row) are **always 8px** from the block above and below — models via `.tab-content { margin-top: 8px }`, settings via `.status-summary { margin: 8px 0 0 }` (the content gap there is provided by `.tab-content`'s margin-top), logs via `.toolbar { margin-bottom: 8px }`, params/downloads via the status bar's `margin-bottom: 8px`.
- **Divider rhythm** (solid separators in the section style, unified 2026-08-29; **14px on both sides of the line**): ① **Primary divider** (`1px solid var(--border)`, between content blocks) — the Card bottom-edge mechanism (body `10px 0 14px`; below the line the whitespace comes naturally from the fixed height of the next block's header); the top-edge variant (Dashboard `.q-section + .q-section`, DownloadCard `.tasks-section`) uses `padding-top: 14px`, and **above the line** it is likewise 14px — on Dashboard from `.q-section { padding-bottom: 14px }`, on DownloadCard from the container's flex gap 8px plus `.tasks-section:not(:first-child) { margin-top: 6px }` to make it up (in task mode it is the first child, so nothing is added). ② **Secondary divider** (`1px dashed var(--border)`, details / secondary content inside a block, e.g. ModelMetaCard `.meta-chips.details`) `padding-top: 8px`, with the space above provided by the `.meta-body` gap of 8px (8/8 symmetric). ③ **Title underline** (group titles with a `border-bottom`, e.g. ParamSummaryCard `.summary-group-title`, DownloadCard `.group-title`) `padding-bottom: 4px`; the **in-card subsection title** of the same family (DownloadCard `.section-title`, block title on the left of the row + actions on the right) matches the group title in size, weight and letter-spacing (`--fs-sm` / 600 / `--color-text-2` / uppercase / `letter-spacing: .5px`) but gets no underline. ④ **Table row separators**: cell `padding: 6px 8px` (§7.5.4 Tables). The internal section bars of dialogs (FileBrowserModal head/foot `12px 14px`, path/save rows `8px 14px`) are dialog-specific sizes and are not part of this scale.
- **Card body (`Card.vue`)**: `a-card :bordered="true"` with its **native inner padding** (the custom `padding: 10px 0 14px` is gone — that declaration was deleted along with the Arco migration and has 0 hits in the code), and the spacing between cards is carried by `.section-card { margin-bottom: 16px }`; the title goes through the `#title` slot (`a-space` holding the title and `title-extra`), the action area through `#extra` + `a-space :size="6"` (see STYLE_TODO #21 and the "card action area" convention of this section); there is no accent bar (the compact variant was removed in 2026-09, one standard title idiom across the whole app).
- **Component padding conventions** (unified 2026-08-29, see STYLE_TODO #21): padding is part of a control's size rather than element spacing, so it is not bound by the gap scale table — but the same kind of element must always use the same value. ① `fs-xs` coloured small badges are uniformly `1px 6px`, and **must be carried by `a-tag size="small"`** (hand-drawn `<span>` pills are forbidden; colours come from the `--badge-*` tokens + `color-mix` translucent backgrounds, see §7.5.7); **a-tag renders no `.arco-tag-content` wrapper** (slot children are attached directly to the `.arco-tag` root), so the `gap` and `align-items` between a chip's segments (key / `=` / value, text / count) are written on the a-tag root class, and the inner text gap takes the scale value `5px` — writing `:deep(.arco-tag-content)` is a dead rule that matches nothing (STYLE_TODO #69). ② `fs-sm` interactive chips are uniformly `3px 8px`. ③ Information display pills (clickable values in the status bar; the old `version-badge` class was deleted with the Arco migration, the sidebar version is `a-typography-text.version`) are uniformly `2px 10px`. ④ Vertical micro-gaps of non-pill rows/bars (hint bars, pagination bars, help hot zones, label underline gap) are always ≥4px. ⑤ Parameter rows `padding: 4px 8px` (§7.5.7). ⑥ Fixed-height filter controls: level filtering uses `a-radio-group type="button" size="small"`, category filtering uses checkable `a-tag` (Arco's default is already 24px tall / `0 8px` inner padding) — do not add extra size overrides. ⑦ Standalone centred empty states (`.empty`) use `padding: 20px`; the remaining empty states are variants with different semantics, each internally consistent (dialog `.fb-empty` `24px 14px`, in-block `.empty-msg`/`.target-recs-empty` `8px`, large-icon LogsPage `.empty-log` `40px 20px`). Optical-alignment exceptions that remain: the Card title's left indent `0 0 0 2px` (compensation for uppercase glyphs).
- **Button groups**: `display: flex; gap: 8px` (page toolbars, inline action areas); dialog buttons `gap: 10px`; card header actions `gap: 6px`.
- **Common control heights**: always the Arco component default (`a-button size=small` 28 / input `a-input size=small` 28 / default 32; buttons inside self-built overlays 28–32); only the TopBar primary action and `--btn-h`(30) are business conventions; win-btn (window controls) at 46 wide is an Electron-specific exception.
- **Tables**: always `a-table` (with `size="small"` the cell inner padding is Arco's own, measured `5px 16px`); **do not customise sticky headers or backgrounds** (`position: sticky` / `--bg-card` have 0 hits in `packages/ui/src` — rules from the hand-drawn-table era, deleted during the Arco migration, do not re-add them). The `col-*` class names are `PresetsPanel`'s **list-row** column-width convention (`.col-name` / `.col-time` / `.col-model`), unrelated to tables.
- **Unified control widths**: the parameter control `label-col` is **fixed at 124px with its right inner padding zeroed out** (**must be `flex: 0 0 124px` + `min-width: 0` + `padding-right: 0`**), **right-aligned** + `margin-right: 8px`, long labels truncated with an ellipsis). Basis of the measurement (STYLE_TODO #72/#73/#78 field results): an off-screen probe (**it must use the label's real font**, the `14px Inter/PingFang` stack — 13px underestimates by 7%) measured the natural width of all 60 row labels; the longest one ("Unified KV Per Slot", measured on the Chinese UI text) = **122.8px** → with 124 available only 1.2px of headroom remains, **so this column cannot shrink any further**. ⚠️ **Arco's `.arco-form-item-label-col` ships `padding: 0 16px 0 0`**: the old recipe "fixed width 140 + `margin-right: 8`" actually yielded `140 − 16 = 124` of usable width (not the 132 the docs used to state), and the real empty gap between label and control was `16 + 8 = 24px` — **the 8px §7.5.4 always stated was never true**. Zeroing the right inner padding makes "column width = usable width", so the same usable value saves 16px of row width and the gap returns to the specified value (#78). Two hard criteria: ① Arco's native `flex: 0 0 auto` lets the label size itself to its text (measured nine different widths between 28–93px), so the controls of the column drift row by row (x 318→380); ② **you cannot reuse the settings panels' `0 1` (shrinkable)** — parameter-row controls (slider + 76px number box + 72px hint slot + 24px restore slot) fill the row, so any shrinkage lands on the label (measured shrinking to 64/83px, misaligning the controls again). Implementation: `ParamRow.vue` applies it uniformly through `:deep(.arco-form-item-label-col)` (each row carries its own `a-form-item` and there is no outer `a-form`, so `label-col-style` is not in play); the three settings panels still use the components' native `label-col-style`, but with the same rules as the Params page (**STYLE_TODO #79**): `flex: 0 0 <W>px` + `min-width: 0` + **`padding-right: 0`** (column width = usable width, the label-to-control gap returns to the specified 8px instead of being eaten by Arco's built-in 16px padding), and **W is the longest label in either language plus headroom** — General 145 (en "When Closing Window" 141) / Appearance 110 (longest in both languages 61) / Advanced 176 (en "Max Concurrent Downloads" 172); `SettingsPage.vue` applies a uniform `:deep(.arco-form-item-label)` ellipsis fallback, so a longer label in any language is truncated rather than pushing the control (asserted row by row by `e2e/web/app.spec.ts` "settings form label geometry (bilingual)": `control left edge ≥ text right edge`, and zero truncation). Inside the control column: `num-input` fills the width (`IntEntryParam`'s `a-space` / `a-input-number` `width: 100%`), the dropdown trigger `dropdown-trigger` is 100% wide, slider items take `flex: 1` and the number item is fixed at **76px** (a 6-digit value `262144` measured `scrollWidth ≤ clientWidth`, 13/13 sliders with zero overflow; the old 88 was a guess), **and the two row-end decorations always live in permanent fixed-width slots**: `.gguf-hint-slot` (`flex: 0 0 72px`) holds the suggested-value chip, `.clear-slot` (`flex: 0 0 24px`) holds the restore ✕, **the chip/button itself is `v-if` (with the `v-if` on the `ToolTip` so no empty host is rendered) while the slot is permanent** — the criterion is "in one column of 60 rows the control width and the slot x each have exactly one value" (#72 once ruled the ✕ "transient state, do not reserve", which measured a leftover control width of `[176, 148]` — two values — plus the hint-slot x shifted left by 28px; after the user's 2026-09-20 annotation it was changed to reserved, see STYLE_TODO #77). **The only element not reserved is the `.dep-hint` warning icon** (4+14px): `syncDependencies` resets a parameter to its default when its dependency is unmet, and only `file`/`dir` types keep their path (`resetDep` returns early), while among the 11 `dependsOn` declarations `file` type is only `spec_draft_model` → that state can hit at most 1 of 60 rows, and reserving 18px permanently for it would push the grid's minimum track from 418 to 436 (losing one column at a 1156 viewport), which is not worth it. **Fixed-width flex slots must always carry `min-width: 0`** (the default `min-width: auto` is blown open by long content: measured, a 72px slot was pushed to 222px by a 30-character alias hint, the control then shrank to 146px and the input's internal width went to 0px).
- **Label column widths must be checked against the longest label in both languages, not just Chinese**: the 124px on the Params page was fixed by #78 from the longest Chinese label (122.8px), but the English side was not measured item by item at the time; measurement found **11 of 60 English labels too wide and ellipsized** (longest 169px, cut by 45px), and STYLE_TODO #80 brought that to zero by **shortening the English `PARAM_LABELS.en` wording** (zh untouched; widening the column would drop a column count, which conflicts with #78, so it was excluded). Implementation: `shared/src/i18n/labels.ts`; regression guard: `e2e/web/app.spec.ts` "form label geometry (bilingual)" asserts row by row that the Params page's 60 rows plus the three settings panels have **zero truncation and no control being pushed** (including `expect(row count).toBe(60)` so that under-rendering cannot pass vacuously). Measurement method: must use the page's real font (`14px Inter, "Segoe UI Variable", "PingFang SC"…`) off-screen; a 13px probe underestimates by 7%.

- **Display fields and form rows (2026-09-07 native-ised, the boxed value box standard is retired)**: read-only field areas use `a-descriptions` (multi-column `:column` + `:span` for full-width fields; copyable values use `a-typography-text copyable`, with `@copy` falling back to the Electron clipboard); settings form rows use `a-form`/`a-form-item` (fixed-width right-aligned labels via the component's native `label-align` + `label-col-style`, row gap 4px). The old boxed value box (26px pill) and the InfoStrip component have been deleted; do not recreate that kind of hand-drawn layout.

#### 7.5.5 Button rules (2026-09: `a-button` app-wide)

The legacy custom button system (`btn`/`action-btn`/`mini-btn`/`tab-btn`/`modal-btn`/`dl-btn`/`fb-btn`) has been deleted entirely; buttons always use `a-button`, typed by semantics:

| Scenario | Usage |
|---|---|
| Page/card primary action (start, save, parse) | `a-button type="primary"` (default size) |
| Inline secondary action (copy, browse, open directory) | `a-button size="small"` |
| Dangerous action (stop, clear, delete) | `a-button status="danger"` (solid, or a `warning`/`danger` outline per semantics) |
| Table row / tight spots | `a-button size="mini"` |
| Icon button (parameter restore ✕ and similar control semantics) | `a-button type="text" size="mini" shape="circle"` (exempt from the "inline text" rule) |
| TopBar window controls (minimize / maximize / close) | `a-button type="text"` + `.win-btn` window-chrome overrides: 46×52 edge-attached hit area, `--radius-control` radius, red hover on the close button; clicks go through the Electron window protocol (Arco has no window-control component) |
| In-page tabs | `a-tabs` (do not assemble them out of buttons again) |

- **Outline / state semantics**: action = primary/accent, danger = danger, warning = warning, all preferring Arco's presets; leave hover states to Arco and do not hand-write background colours.
- **Inline text**: action buttons in the content area always show icon + label (`#icon` slot + text); icon-only action buttons are forbidden; exemptions: win-btn window controls, the input box's allow-clear ✕, the restore ✕, the navigation chevron — these are control / navigation / disclosure semantics, not action buttons.
- **Button groups**: `display: flex; gap: 8px` (page toolbars, inline action areas); dialog button groups gap 10px; card header actions gap 6px.

#### 7.5.6 Overlays (2026-09 glass system removed)

- Glassmorphism was **deleted outright** along with the completed migration: the `--glass-*` tokens, the `.glass-layer` class and `backdrop-filter` all have 0 hits in `packages/ui/src` (not even the compatibility mapping remains, verified 2026-09-19), and **no new code may use `backdrop-filter`**.
- Dialogs (`a-modal`), dropdowns (`a-dropdown`/`a-select`/`a-trigger`), tooltips (`a-tooltip`) and Popconfirm all use the Arco component defaults: an opaque panel + Arco's own shadow/animation, with the popup teleported to body. **Self-built overlays are now zero** (the engine help panel moved onto `a-popover`; the criterion is `e2e/web/help-popover.spec.ts`); none may be added.
- Overlay content typography: panel radius / border / background use the Arco defaults; item hover states (`a-doption`) use the Arco defaults, no hand-written backgrounds.
- **Semantic obligations for overlays, dialogs and navigation (2026-10-07 keyboard-accessibility pass)**: Arco supplies no semantics in these three places, so we must add them — this may **not** be waved away as "a library problem". Measured evidence: `grep -rl aria-modal node_modules/@arco-design/web-vue/es` returns **0 hits**, `a-modal` has no autoFocus, no focus trap and no focus return; `a-menu-item` renders as a DIV with no `tabindex` and no `role` (40 consecutive Tab presses never land on a nav item, and `el.focus()` is refused), while the sidebar is the *only* entry to the Params and Settings pages. Where it lands: (1) `Sidebar.vue` sets `role="navigation"` + `aria-label` on `a-menu` and gives every `a-menu-item` `role="link"`, `tabindex="0"`, `aria-current="page"`, with Enter/Space routed through the existing `navigate()`; (2) the three dialogs (`FileBrowserModal` / `CloseDialog` / `ConfirmModal`) carry `role="dialog"` + `aria-modal="true"` + `aria-labelledby`, with focus handled by `composables/useDialogFocus.ts` (move in on open, Tab cycles only inside the dialog, return to the trigger on close); (3) the self-built overlays exempted by §7.5.6 must ship a keyboard entry — the engine-help panel in `GeneralPanel` uses an `a-button` base with `aria-label`/`aria-expanded`/`aria-haspopup`/`aria-controls`, Enter opens and Esc closes, and the hover timers are only an accelerator. Forms follow the same rule: `a-form-item` never emits `label[for]` (the prop does not exist), so every control gets its name from our own `aria-label` (applied uniformly across the six param control types for all 69 rows, see §7.5.7). **Inner focusable nodes additionally need `directives/innerAriaLabel.ts`**: Arco's Slider never passes `$attrs` to its handle (`slider-button.js` does `mergeProps($attrs)` but receives nothing), and Select has no `input-attrs` prop while the keyboard stop is the inner `input` — so the directive sits on a **single-root host** (each row's `a-form-item`) and pushes the name down to the inner nodes. Note that Vue **silently skips custom directives on multi-root components** (measured: it works on `<a-slider>`, leaves no trace at all on `<a-select>`), which is exactly why the directive hangs on the form item rather than on the control. After this was closed: 121 tabbable controls on the Params page and 28 on Settings, **zero without a name** (identical in both languages), and the residual registry in `e2e/web/a11y.spec.ts` is now emptied to `[]`.
- **Multi-line tooltips must go through the `#content` slot**: the `.arco-tooltip-content` rendered from `a-tooltip`'s `content` prop is `white-space: normal`, so multi-segment text such as `label\nhelp` collapses into one line (measured height 30px). `ToolTip.vue` was changed to a slot plus its own `.tooltip-text { white-space: pre-line }` (even though the popup is teleported to body the scoped attribute travels with the element, so the style applies; measured three text segments at height 74px). New multi-line overlays must reuse the `ToolTip` component and must not fall back to the `content` prop.
- **Boundaries of the hint mechanism (STYLE_TODO #74/#75, converged 2026-09-19)**: **page-level elements and the few fixed chrome elements always use `ToolTip`** — the 8 TopBar buttons (including win-btn), the 2 copy buttons in the status bar, card-header / toolbar action buttons, the parameter status bar's statistics block and its three action buttons, the settings panel buttons, the file-browser dialog's "Up" button, the download card's site / directory buttons, the service status card's status badge and buttons, and the three places on a parameter row (label / suggested-value chip / restore ✕). The native `title` is not theme-controlled (it stays a system-white box in dark theme), delays for about 1s and cannot carry multi-segment text, so it is banned in all of these.
- **The three cases that keep the native `title` (explicit boundary — do not "fix them in passing")**: ① the `title` **prop** of Arco components (`a-modal` / `a-popconfirm` / `a-statistic` / `a-dgroup`) and `iframe title` (an accessibility name) — these are not overlays; ② **hints on `v-for` data items** (model table rows, download task rows, preset rows, the chips in `ParamSummaryCard` / `targetRecs`) — mounting one Arco trigger instance per item contradicts the hot-path rules of §7.1; ③ **truncated-value hints** (long paths and long URLs in `.mono-val` / `.file-name` / `.task-name` / `.task-error` / `.summary-label`) and `a-input :title` (a wrapping host would disturb the form control box). Measured, native overlays repo-wide went from **60 down to 33 `:title=`** sites (plus 1 `iframe title` accessibility name and 6 component props, 34/40 in total by grep's counting), converting 26 sites / 9 files; `<ToolTip` usage is at **35 sites / 16 files**.
- **Two measured caveats when wrapping an interactive control in `ToolTip`**: ① wrapping `<a-button>` changes geometry by zero (host and button share the box; the `ParamRow` restore ✕ is still 24×24 with a 38px row height), but when the element carries its own `v-if` **the `v-if` must move onto the `ToolTip`** (otherwise an empty host and an empty overlay are rendered; a `v-if`/`v-else` pair must move onto both `ToolTip`s together so the directive chain stays adjacent); ② **wrapping an `a-dropdown` trigger in a `ToolTip` still works** — the Trigger events sit on the host, the click is triggered by bubbling from the button, and the popup anchors to the host box (measured: the TopBar model dropdown's centre x=493 matches the trigger centre, and on the Params page the performance-target dropdown with `position="bl"` keeps its popup x equal to the trigger x=723).
- **Namespace for non-scoped style blocks** (mandatory when the popup is teleported to body): **every top-level selector in the block must contain at least one component-private class**, never composed only of Arco global class names (it would otherwise hit every other usage site globally). Patterns: ParamsPage `.target-menu …`, GeneralPanel `.exe-help-panel …`, DownloadCard `.arco-dropdown-list:has(> .url-history-item) .arco-dropdown-group-title` (`a-dgroup` renders as a Fragment and its title `li` cannot carry a private class, so `:has()` is used to look backwards). Frozen as audit rule 11.
- Exception: the white translucent hover on the dark-blue status bar (`rgba(255,255,255,.15)`) is **surface tinting**, not elevation; the chip count background (`color-mix` translucent background) belongs to the same family — neither is folded into the shadow tokens.

#### 7.5.7 Common patterns

- **Parameter row** (carried uniformly by `ParamRow`, all controls Arco): row container `padding: 4px 8px` + radius `var(--radius-row)`, transparent border by default; hover background `--color-fill-3` + border `--color-border-2`; **when value ≠ default the border becomes `rgb(var(--orange-6))`** (the same colour family as the restore button); an unmet dependency gets the same-coloured outline + a background tint + an `a-tooltip` warning icon; file/directory types render an `a-input-group` file picker.
- **Parameter rows must not enable `allow-clear`** (STYLE_TODO #74): Arco's own clear ✕ (`.arco-input-clear-btn`, `visibility: hidden` normally, revealed on hover when there is a value) would sit next to the row-level "restore default" ✕ = two ✕ marks in one row; and it writes an **empty string** rather than the parameter's default value (clearing `host` triggers `err_invalid_host`), which contradicts the meaning of the row-level button. The restore entry on a parameter row is unique — the row-level `.clear-btn`.
- **The suggested-value chip family is unified** (`.gguf-hint` on parameter rows / `.suggestion-chip` on the Models page's "Suggested Parameters" / `.rec-chip` for performance-target cascade suggestions, measured identical at every tier): `a-tag size="small"` (h20 / radius 2px / padding `0 8px`) + `font-family: var(--font-mono)` + `font-size: var(--fs-sm)`; the two families carrying `key = value` also set `gap: 5px` + `.chip-key` (`rgb(var(--primary-6))` 600) /`.chip-eq` (`--color-text-3`) /`.chip-val` (`--color-text-1`) tri-segment colouring (Arco renders no `.arco-tag-content`, so gap/align go on the a-tag root class, §7.5.4 ① / #69). Numbers always go through `v.toLocaleString()` (all three families share the same wording, measured "32,768" is not an outlier; the largest numeric field currently on a parameter row is 7 digits (`context_length` ≤ 262,144), so thousands separators do not eat the 7-glyph ellipsis budget, **but re-measure if a field with ≥7 digits is ever attached**).
  - **Colour and cursor follow one single rule**: `color="arcoblue"` blue background + `cursor: pointer` = **the chip itself is clickable to apply**; grey background + `cursor: help` = **display only, hover to read the explanation**. The read-only tier originates in the backend: `buildSuggestions` deliberately produces no suggestion for pure reference information (`context_length` training limit, `rope.freq_base`, etc.) — `-c` default 0 already loads from the model, so per-item suggestions would only add confusion (comment in `core/src/gguf-meta.ts`) — hence a parameter row can show a grey "value shipped with the model" chip (measured 2 of 8: context length / chat template). **The grey tier must not keep `cursor: auto`** — differing from the blue tier only in background colour with zero hover feedback, it reads as "a broken suggestion chip" (appended under #77). The same vocabulary is used for the `.dep-hint` warning icon.
- **GGUF suggested-value chip** (`.gguf-hint`, inside the fixed **72px** permanent slot `.gguf-hint-slot`): long values **must be middle-elided in JS** (head 4 + `…` + tail 2, **7 glyphs** being the measured ceiling: mono 12px ≈ 7.03px/glyph → 7 glyphs 49.2 + Arco's native `0 8px` padding + 1px border ×2 = 67.2 ≤ 72, leaving 4.8px of font-fallback headroom). CSS `text-overflow: ellipsis` cannot be relied on here — `a-tag` is `inline-flex` with no content wrapper (§7.5.4 ① / #69, same root cause), so the CSS ellipsis never applies and a 30-character alias suggestion gets hard-cut into a hintless "Qwen3-32B". The tail is kept because the quantization suffix / unit is the distinguishing information; **the full value + the parameter name + the action hint, all three segments, go into a `ToolTip`** (native `title` forbidden — it cannot carry multi-segment text).
- **Parameter grid**: `param-grid` (the Params page) `repeat(auto-fill, minmax(434px, 1fr))`, **no `max-width` cap** (since 2026-09-20, see STYLE_TODO #76), gap `4px 14px`, single column at ≤720px; decoration uses Arco's primary blue `rgb(var(--primary-6))` throughout.
  - **Derivation of the 434px minimum track**: the minimum comfortable width of one parameter row = border 2 + row inner padding 16 + label column 124 + 8 + control ≥164 (slider track 80 + gap 8 + number box 76) + 4 + hint slot 72 + 4 + restore ✕ slot 24 + 4 + **dependency-warning slot 12** (STYLE_TODO #81 tier 1, the fourth place where #77's "permanent slot" pattern had been missed) = **434** (the #78-era equivalence `control width = track width − 254` becomes `− 270`). Evolution: when #76 wrote 400 the row's 2px border and 16px inner padding had been left out of the sum (measured: on a 413px track only 171 was left for the control and the track was 75px, below #73's 80px floor); #77 added the permanent restore-✕ slot +28 → 450; **#78 recovered two instances of bloat** — the 16px right inner padding Arco puts inside the label column (zeroed, usable width unchanged) + number box 88 → 76 (6-digit values measured overflow-free) + hint slot 76 → 72 (ellipsis budget 8 → 7 glyphs) = −32 → **418**; #81 then added the dependency-warning slot plus its 4px gap → **434**. **Never lower the track floor (80px) in order to buy extra columns**: at 380px a 1920 viewport does fit 4 columns but the track is squeezed to **55px**; at 340px, 1440 fits 3 columns with a **31px** track.
  - **Column count is stated as arithmetic, not per viewport**: track 434 + column gap 14 ⇒ 2 columns need ≥ **882** of usable width inside the card, 3 ≥ **1330**, 4 ≥ **1778**, 5 ≥ **2226**. The old "1156/1280/1440 → 2 columns, 1600/1728/1920 → 3 columns" style of note recorded viewport-by-viewport experience from the 418 era and goes collectively stale the moment the track changes, which is why `ParamsPage.vue` now carries only the formula; apply it per viewport as needed (example: a 1156 viewport gives a 840–850 grid, which is < 882, so it is a single column today rather than the "2 × 418 absent the 12px content scrollbar" note of that era).
  - **Why there is no cap (measured)**: the old `max-width: 1160px` hard-capped the layout at 3 columns, and once the card's usable width reached ≥1326px everything beyond became blank space on the right — 1920 wasted **486px**, 2560 wasted **1126px** (almost half the width unused). Column count now grows monotonically with width and `waste=0` (the table below was re-measured per viewport after #78's compaction; compare #77's 450: 1600 comes back from 2 to 3 columns, 2560 from 4 to 5):

    |---|---|---|---|---|---|
    | 1156 | 840–850 | **1 × 840** (2 × 418 without the 12px content scrollbar) | 586 | 502 | 0 |
    | 1280 | 974 | 2 × 480 | 226 | 142 | 0 |
    | 1440 | 1134 | 2 × 560 | 306 | 222 | 0 |
    | 1600 | 1294 | 3 × 422 | 168 | 84 | 0 |

Locking 1156 into two columns would need a minimum track ≤413, at the cost of the slider track dropping to 75px (below the 80 floor) — per #76, "control usability comes before column count", so that trade is rejected.

  - The alignment invariants hold at every column width (Playwright measured all 60 rows per viewport): label column width `[124]` a single value, **control width exactly one value per column (no longer `[176, 148]`)**, hint-slot x and ✕-slot x one value each per column (appearing/disappearing no longer shifts anything), 0 rows of label truncation (the criterion is `scrollWidth > clientWidth` on the element that carries the text, not on the label itself — Arco wraps the text in `.tooltip-host`, so comparing only the label misses cases), 0 tick nodes, 0 chip clipping, 0 overflow in slider number boxes.
- **Filter chip selected state**: the hover/selected states of a `checkable a-tag` **always use Arco's own states**; do not override Arco's internal state classes such as `.arco-tag-checked` (audit rule 12); when a visibly selected background is needed, use Arco's `color` prop (DownloadCard's category filter takes `color="arcoblue"`, selected background = `rgb(var(--arcoblue-1))` / dark `rgba(var(--arcoblue-6), .2)`, the same source as `--row-selected-bg`). Filter group spacing 6px (§7.5.4 scale table).
- **The two approved list-row variants** (a third is forbidden): ① **native row** — `a-list` defaults (`split` separators + `size` padding), e.g. PresetsPanel; ② **compact selectable row** — `a-list :split="false"` plus a row container carrying its own `border` / `--radius-row` / `--color-fill-2` background and padding (zeroing the row padding must match Arco's specificity: `:deep(.arco-list-content-wrapper .arco-list-content > .arco-list-item) { padding: 0 }` — a plain `:deep(.arco-list-item)` is beaten by the `size="small"` rule and has no effect, measured on a real machine as 9px 20px); this is the variant that hosts whole-row click selection, the `--row-selected-bg` selected state and in-row badges, e.g. DownloadCard `.file-item` / `.result-item`, FileBrowserModal `.fb-row`. Apart from `padding: 0` no `a-list` internal style may be overridden (separators use the `:split` prop; `.arco-list` / `.arco-list-item` have no background colour of their own, so there is nothing to override there). **Two implementation points measured under STYLE_TODO #68**: ① Arco wraps the default slot into `.arco-list-item-main > .arco-list-item-content` (both `display: block`), so the row container's own `display: flex` + `gap` all miss their target — you must write `display: contents` for those two levels before the slot children become the row's flex items (`flex: 1` expands, `gap` applies, badges right-align, the text ellipsis works); ② the row class and `.arco-list-item` are **the same element**, and the parallel selector written to beat Arco's `size="small"` has higher specificity, so the row's `padding` can only live inside that rule (writing it on the row class gets zeroed by that very rule).
- **Layout idiom**: content areas always use flex (`display: flex` + the gap scale); `display: grid` is limited to this section's `param-grid`.
- **Status indication**: hand-drawn small status dots are gone with the Arco migration (`width: 7px/8px` + `border-radius: 50%` dots have 0 hits in `packages/ui/src`) — `StatusTag` carries them with `a-tag` + `a-spin`, the status bar with `a-tag` colour pills; `border-radius: 50%` is kept only for switch knobs / slider thumbs / circle icon buttons and other Arco-native shapes (STYLE_TODO #50 🟢 fixed, 2026-09-09).
- **Hover hint text colour**: `color-mix(in srgb, rgb(var(--success-6)) 12%, transparent)` background + the same colour for border/text (e.g. PresetsPanel's applied-msg).
- **Download badge system** (carried natively by `a-tag size="small"`, hand-drawn `<span>` forbidden; box model per §7.5.4 ①: `1px 6px` + `--radius-pill`; constant across both themes): ① **category family** `.file-cat` — colour from `--badge-cat-*`, background `color-mix(in srgb, var(--badge-cat-*) 14%, transparent)`, `cat-other` using `--color-text-3` + `--color-fill-3`; ② **quantization family** `.quant-badge` — keyed by `parseQuantization`'s family onto `--badge-quant-*` (14%, 16% for legacy/fp32); ③ **source family** `.source-badge` — **neutral palette** (`--color-text-2` + `--color-fill-2`), claiming no hue and distinguishing itself by text (the hue budget is already spent by ①②, so any colour would collide with the attribute badge on the same row); ④ `.rec-badge` solid primary + `--primary-fg`. **The source identifier appears once in the "Model Files" section title and once in the download task row**, and is not repeated on the parse-information line.
- **Motion**: `--ease-*` has been flattened to `ease`; durations come in two kinds — **interaction feedback** uses `--dur-fast` (0.16s) and must stay ≤0.3s, while **ambient hints** (persistent motion meaning "this state is still ongoing", currently only the "new logs" pulse in `ConsolePanel`) use `--dur-ambient` (2s) and may repeat infinitely, because a single fade-in cannot express "still happening". Both kinds may **only animate transform/opacity**, layout animation is forbidden, and literal durations/easings must go through tokens (`style-audit` rule 14 blocks literal durations and `infinite` in `transition` / `animation` outright; rule 8 only covers "layout properties must carry `var(--dur-*)`"); **buttons do not scale on press** (press feedback = background/border colour change); everything is off under `prefers-reduced-motion` through a single mechanism — the global rule in `reset.scss`, with no JS-side snapshot.
- **Copy buttons unified** (2026-08-29, see STYLE_TODO #26): inline copy actions always use `a-button size="small"` + `#icon` (`Icon name="copy" :size="12"`) + label (copy address `copy_url` / copy model name `copy_model` / copy command `copy_cmd`), with the label temporarily switching to "Copied" as feedback after a click; icon-only mini buttons are not used for this. Content items (value pills / URL bars etc.) are paired with a text description label (styled per the `.info-label` semantics: secondary colour, 8px against the content). **The status bar is the exception**: the value *is* the button — an `a-button type="text" size="mini"` base + status-bar chrome overrides (pill / white text / `--statusbar-hover` surface tinting), click to copy + tooltip + a "Copied" tag.
- **Model alias derivation** (2026-08-29): on `set(MODEL_KEY)` the `alias` parameter is derived automatically = the model file name without the `.gguf` extension (`modelBaseName`, shared), and command building carries `-a/--alias` automatically (the model name on the API side carries no extension); switching models updates the alias along with it, and a preset that carries a model but stores no alias gets one derived; the "current model" display (Overview status card / status bar) prefers the alias, falling back to the extension-less file name.
- **App logo unified** (2026-08-29, see STYLE_TODO #29): every place the logo appears uses the `AppLogo` component (`components/common/AppLogo.vue`, `size` prop for the edge length) — one and the same svg asset (`assets/app-icon.svg`, the same source as the packaged / taskbar icon) with a consistent pill radius (`--radius-pill`); places: TopBar (20px), Settings → About brand header (40px + app name + version), browser tab favicon (index.html `link rel="icon"`, same source). Any new place that shows the logo must reuse this component; `import app-icon.svg` directly or scattering `<img>` tags is forbidden.
- **API address semantics converge on the server store as the single source** (2026-08-31): every "API address" display / copy in the UI reads only `server.apiUrl`, and **pages must not derive it locally from `server.url`/`host`/`port`**. Inside the store `apiUrl` is bound to the real service state — `running` returns `url` (falling back to `http://host:port` when it is empty), `starting` returns the derived address, `stopped` returns **an empty string**. Reason: the `onStatus` event updates only `status` and does not refresh `url`, so after a stop `server.url` still holds the previous launch's address, and a page reading `url` directly would show a stale, dead URL. The presentation layer renders empty values as a placeholder (`—`/`status_stopped`) with the label slot and the copy button permanent (`disabled` when there is no value), so the row structure does not jump before and after a run. Current consumers: the Overview service status card (`ServiceStatusCard`), the status bar (URL clickable to copy, the whole entry disappears after a stop), WebUiFrame (iframe src, keeping its own `running` gate as a second lock). Any new place showing an API address must reuse `server.apiUrl`.
- **Document semantic skeleton (2026-10-07, STYLE_TODO #92)**: ① **exactly one `main` landmark app-wide** — `AppLayout`'s `.app-content` is it, so the page root `PageFrame` must be a plain `div` (Arco's `a-layout-content` renders as `<main>`, and nesting one more gives `main > main`; the Models page nests PageFrame twice, measured as three `main` elements before the fix; putting `role="none"` on the inner layer would only mask the symptom, so a layer was removed rather than papered over). ② **exactly one `<h1>` per page**, rendered in one place by `PageHost`: the element is Arco's `a-typography-title :heading="1"`, and its text comes from the current route's `nav.labelKey` in the `features` registry (the same source as the sidebar label, so the seven pages no longer each write their own title and a new page cannot structurally forget one). Page names only ever appear in the sidebar and no page carries a visible big heading, so this is an **sr-only heading** — `position: absolute` + 1×1 + `overflow: hidden` + `clip-path: inset(50%)` (written locally in `PageHost.vue`; `theme.scss` gains no global utility class for it); **never `display:none` / `visibility:hidden`**, which screen readers honour too. It sits **outside** `.page-host`, not inside: `.page-host > *` is the readiness gate four e2e specs share for "the asynchronously loaded page component has mounted", and a synchronously rendered title placed inside would be hit first and spin that gate idle. ③ **card section titles are `<h2>`** (in one place, `Card.vue`): a plain card puts the text in an `<h2>`, a collapsible card uses the WAI-ARIA APG accordion shape `<h2>` wrapping an `a-button` (heading wraps the button; the reverse — stuffing `role="heading"` into the button — would swallow the button semantics). Size, weight and line-height **inherit Arco's own card-header declaration** (`margin: 0; font: inherit`, measured 16px / 500 / 1.5715) instead of inventing a heading tier (Arco `a-typography-title`'s h2 tier is 32px, which in a card header would be a redesign); before and after, 22 cards across 5 pages match item by item on header / title box / first content box. ④ **Status changes must speak**: the status row's `a-space` in the Overview status card passes `aria-live="polite"` straight through (Arco Space does not disable `inheritAttrs`, so the attribute lands on the `div` it renders) and **adds no wrapper element** — the criterion requires the live root to be the very same node as the status row, since wrapping it would be a second geometry (card heights and permanent slots are hard criteria of #81/#82). The "Failed to Start / Crashed" wording already arrives on `ServerStatusEvent.stop`, so announcing it is only that status text changing: **no new IPC channel and no new renderer-side timer**. Criteria and deletion experiments: `e2e/web/semantics.spec.ts`.
- **Forbidden**: `style="color:#..."` inline colour values inside components (except dynamic state colours such as the StatusBar status dot); bare `rgba(...)` shadows/backgrounds that are not tokens; per-row / per-list-item backdrop-filter.

#### 7.5.8 Consistency checklist (compare before changing UI)

- [ ] All colours go through Arco CSS Variables or the `theme.scss` business tokens (`#fff` only as text on a solid primary background)
- [ ] Text contrast ≥4.5:1 (WCAG AA), informational text uses the `--fg-*` role tiers (Arco's `--color-text-3` and state `*-6` colours as text measure 2.57–3.71 and do not clear it); text is never dimmed with `opacity` (use a colour token instead)
- [ ] Overlays always use an Arco component (`a-popover` / `a-dropdown` / `a-modal` / `a-tooltip`) and its own shadow, opaque surface, stacking and entry animation; no self-built overlay, no bare `box-shadow`
- [ ] Font sizes go through `--fs-*`; line-height per the §7.5.1 text system (body ≥1.3, `1` only for icons / single-line centring); font weight only 400/600/700
- [ ] Radii use the Arco default or `--radius-*` (4px; only the 2px track / 50% circle are exceptions), spacing conforms to 7.5.4 (gap only 4/5/6/8/10/12/14)
- [ ] Controls are always Arco components (button / input / select / switch / dialog / overlay), no new custom interactive controls; **action buttons in the content area are always inline text** (icon + label; exemptions: win-btn window controls, the search box's clear ✕ (**parameter rows must not enable `allow-clear`**, see §7.5.7), the parameter restore ✕, navigation ↑, the disclosure chevron — control / navigation / disclosure semantics)
- [ ] Button groups use flex + gap (8px standard)
- [ ] No `backdrop-filter` anywhere (the glass system has been removed)
- [ ] Every top-level selector of a non-scoped style block contains a component-private class (bare Arco global class names forbidden, §7.5.6)
- [ ] No Arco internal state classes overridden (`.arco-*-checked` / `-active` / `-selected` / `-disabled` etc.); filter / selected states use Arco's own states or the `color` prop
- [ ] **Button colours are never overridden**: an `a-button`'s colour comes only from `type` + `status`, and clearing AA is done by stepping the colour-scale variables Arco reads (a `color` override freezes the hover/active text colour — measured divergence between border and text, §7.5.1); any exception must be registered with a reason in `BTN_COLOR_ALLOW`, check 18 of `style-audit`
- [ ] Badges / pills are always carried by `a-tag`, never hand-drawn `<span>` pills; badges take colour per §7.5.7's three families (source family neutral, claims no hue); **chips of the same family stay on the same tier** (the three suggestion families = `size="small"` + mono + `--fs-sm` + Arco's native `0 8px` padding, size/padding overrides forbidden; blue backgrounds are reserved for "the chip itself is clickable", §7.5.7); list rows use only the two variants of §7.5.7, and layouts avoid grid (except `param-grid`)
- [ ] **Decorations inside a row / bar always live in permanent fixed-width slots** (slot permanent, content `v-if`): appearing or disappearing must not change the width or the start position of any other element in the same column (criterion = the column's distinct values converge to 1, §7.5.4 "Unified control widths" / STYLE_TODO #77)
- [ ] Animations only touch transform/opacity, with durations taken per kind (interaction feedback `--dur-fast`, ≤0.3s; ambient hints `--dur-ambient`), switched off under `prefers-reduced-motion` by the single global rule in `reset.scss`
- [ ] **Keyboard reachability and naming**: every page is reachable by keyboard (sidebar `a-menu-item` carries `role="link"` + `tabindex` + `aria-current`, because Arco gives none); icon-only buttons carry `aria-label`; form controls carry `aria-label` (`a-form-item` never emits `label[for]`); the bar is "zero visible interactive controls without an accessible name", not "it looks clickable"
- [ ] **Dialog semantics**: any popup container carries `role="dialog"` + `aria-modal="true"` + an accessible name, focus moves in on open, Tab cycles only inside, and focus returns to the trigger on close (`useDialogFocus`) — Arco 2.58 provides none of this
- [ ] **Semantic skeleton**: one `main` landmark app-wide (the page root `PageFrame` is a plain `div`, not a second `a-layout-content`); exactly one `<h1>` per page (when the page name only appears in the sidebar it is an sr-only heading rendered in one place by `PageHost`, its text coming from the same `features` registry as the sidebar); card section titles are `<h2>` (size inherited from Arco's card header, no extra heading tier) — criteria and deletion experiments in `e2e/web/semantics.spec.ts`, rules in §7.5.7
- [ ] **Status changes speak**: a status row that flips on events carries `aria-live="polite"`, and the live root **is that very row** (the attribute passes through to the Arco component; no new wrapper element that would create a second geometry); never add an IPC channel or a renderer-side timer just for the announcement
- [ ] **Library-owned text follows the UI language**: Arco keeps its own i18n (default `zh-CN`), so a language switch must call `useLocale()` and update `html[lang]` in the same step — the single place is `stores/i18n.ts`; the criterion lives in `e2e/web/arco-locale.spec.ts` (zero Chinese residue across the seven pages in English, with a Chinese positive control)
- [ ] **Icon semantics reconciled**: one Arco glyph carries exactly one semantic name (historically `folder` and `folder_open` were both the plain folder, so "go up one level" and "open directory" looked identical) and the glyph must match the action; wrong or deleted names are caught by the `IconName` type at `vue-tsc`, while one-glyph-one-name and zero-consumer names are caught by gate check 21 — not by memory
- [ ] Both dark and light themes checked ( `html[data-theme]` + `body[arco-theme]`; the console / command preview keep a constant dark surface)
