# Key design decisions

> Language: English · [中文](../zh/design-decisions.md)
> Scope: Record of the key design decisions and the trade-offs behind them.
> Index: [README.en.md](../../README.en.md) · Related: [architecture.md](architecture.md)

1. **Param emission rule (refactored 2026-08-29, replaces the old `_enabled` enable mechanism)**: a parameter has no separate enabled/disabled state — a flag is emitted only when the value ≠ the default (checkbox: `flag` when ticked, `invert_flag` when unticked (a switch with no always-on flag emits nothing when unticked); empty strings are skipped; dependency gating applies), so the command line contains only the parameters the user actually adjusted. The old scheme, which recorded enabled state explicitly in a `_enabled` JSON encoding, has been removed: a standalone enabled bit created a third source of truth ("value / enabled bit / default") and conflicted with the dual-track model where "preset = a plain value snapshot" (`buildCommand` reads a legacy `_enabled` and simply ignores it).
2. **GGUF smart suggestions**: streaming reads (64KB blocks) + an LRU cache (cap 32) — memory stays flat and re-parsing is avoided.
3. **Secure IPC**: `contextBridge` + `contextIsolation` + `clonePlain` serialization; the renderer process has no Node access.
4. **Cross-version compatibility**: a generic listening check (matches "listening" + "http"/"server") + inline llama-server detection inside the user-selected directory.
5. **Resumable downloads**: Range header + append writes, so an interrupted large-model download can continue where it stopped.
6. **Window geometry persistence**: the new `x,y,width,height` format with backward compatibility for the old `WxH` format, saved with a 500ms debounce.
7. **Hot reload in production**: the `LLAMA_DEV_SERVER_URL` escape hatch lets even a production build connect to a local Vite dev server.
8. **Process-tree cleanup**: on Windows `taskkill /F /T /PID` kills the whole process tree so no child process is left behind.
9. **IPC synchronized in three places + generated artifact must match**: `shared/src/types/ipc.ts` (the single source of truth) → the generated `apps/desktop/src/preload/ipc-constants.cjs` → the API wrappers in the preload `index.cjs`. `verify-ipc-sync.cjs` actually verifies three things: the generated file is not stale, `index.cjs` has not regressed to inlined constants, and **every channel constant has an API wrapper reference in `index.cjs`** (a missing binding fails the check). Note: the "four layers, including `env.d.ts`" wording in earlier docs does not hold — the script never checks `env.d.ts`, and `packages/ui/src/env.d.ts` is only a Vite environment declaration, unrelated to IPC channels (verified 2026-09-20).
10. **Leak-proof packaging**: the beforePack/afterPack hooks handle the pnpm symlinks so the `asar` contains only `dist/*.js` runtime files, excluding sources, tests, configuration and other development resources.
11. **Dynamic presets directory**: preset files are stored in the `presets/` subdirectory of the model directory, kept together with the model files instead of scattered across locations.
12. **Packaging robustness**: on Windows junctions are detected via `realpathSync`, retries plus `rename+rd` clear locked files, and afterPack restores the junctions — guaranteeing that neither the development environment nor the production package gets polluted.
13. **Injectable network transport**: the `DownloadTransport` / `HfHttpTransport` interfaces let the Electron main process inject a transport based on the `net` module (the Chromium network stack), working around hf-mirror.com rejecting the BoringSSL TLS fingerprint of the Node bundled with Electron. Only `hf-mirror.com` goes through the injected transport; other sources (ModelScope and the like) keep using `node:https`, which preserves unit-test mock compatibility.
14. **Online performance measurement (removed as a whole on 2026-09-04 together with the "Performance test" feature; kept here for reference)**: `llama-bench` and similar CLIs cannot evaluate DFlash/speculative decoding, so the performance test instead used the `--metrics` endpoint of a running llama-server plus completion `timings` (the same source as `draft acceptance` in the logs), reading real throughput and the DFlash acceptance rate over HTTP issued through the main process's `net` module (no CORS restrictions).
15. **Restart-race avoidance**: everything goes through `Launcher.restart()` (it waits for the old process to `exit`, then starts the new one), avoiding the `already running` race of a manual stop→start. (The original UI-side two-phase wait `waitRunning` was removed along with the performance-test feature, 2026-09-04; restart-race protection is now carried by `Launcher.restart()` alone.)
16. **Dependency-linked cleanup**: `syncDependencies` clears downstream parameters whose `dependsOn` condition is unmet according to the declaration (preventing leftover invalid flags such as `-md`/`--mirostat-lr` from being emitted), and distinguishes the dependency scope of external draft types (draft-simple/eagle3/dflash/dspark) from MTP/ngram.
17. **DFlash auto-detection**: when the model changes, a dflash draft model in the same directory is detected and `draft-dflash` + `-fa on` + n_max 15 are configured automatically (aligned with the 16-positions-per-block semantics of Muse-Glimmer DFlash); switching back to an external draft type re-runs detection and fills the path in again.
18. **Memory-parameter baseline (measurement-driven)**: `cache_type_k/v` (q8_0), `load_mode` (none), `fit` (off) and `kv_unified` (off, always emitting `--no-kv-unified` through `invert_flag`) are built in as **baseline recommended defaults**. **The emission semantics must be told apart (verified 2026-09-20: `command-builder.ts:72` skips when `v === p.default`)**: the first three are dropdowns, and when their value equals the default they are **not passed to the command line** — what they actually establish is the "default tier declared by the UI/session" layer, while the backend keeps its own default (which happens to point the same way); of the four, only the checkbox `kv_unified` **always emits** `--no-kv-unified` through `invert_flag`. The original sentence "naturally emitted under the 'value ≠ default' rule" conflated the two mechanisms and has been corrected. Basis: `docs/archive/experiments/plan-kv-split-cli-test.md` (measured on an AMD 7900 XTX 24GB with b10429 Vulkan): the long-context combination of f16 KV + mmap + fit on exhausts 32GB of system RAM and freezes the machine; q8 KV lowers the VRAM requirement of 27B@262K from ~35GB to ~25.7GB, `--load-mode none` releases the host buffer holding the weights after loading, and `--fit off` avoids the degradation caused by fit aborting when ctx/ngl are given explicitly (25.7 vs 36.6 tok/s).
19. **KV tiering mechanisms are not exposed (`-cram`/`-kvu`/`--cache-idle-slots`)**: measurements show the AMD driver's transparent GTT paging takes over VRAM overflow before llama.cpp's KV memory tiering ever gets a chance (`-cram 0` and `8192` behave identically), so these are deliberately kept out of the UI for now; should NVIDIA cards be supported later (where an allocation failure does not page out), they can be exposed as needed.
20. **Negative parameter list (measured as not recommended)**: `-nkvo` (KV entirely in memory: on hybrid-architecture models it measured 2.7x slower and produced garbled output), partial `-ngl` layering on dense models (measured 4.7x slower — offload everything, or use `-ncmoe` for MoE), and a large `-ub` (peak memory 4.4x + decode -46%, keep the default 512).
21. **Dual-track parameter logic (2026-08-29, confirmed with the user)**: parameter editing runs on two tracks — the **session track** auto-persists to `settings.session_values` + `session_baseline` (800ms throttle, restored across restarts, never touches the preset files, so nothing can be "changed and forgotten to save"); the **preset track** writes `<models_dir>/presets/*.json` only on an explicit save. `hasChanges` (orange outline on changed rows / an orange dot in the sidebar) is computed key by key against the session baseline `SessionBaseline { preset_name, values }` instead of the coarse-grained "diff against factory defaults" judgement.
22. **Loss-prevention confirmation on model switch + baseline visualization (2026-08-29, confirmed with the user)**: unsaved changes are detected before switching models or applying GGUF-suggested parameters, and `confirmDiscardDirty` rebuilds the temporary baseline only after confirmation (preventing silent loss). The baseline state was originally surfaced by `BaselineBadge` from two entry points (top of the Parameters page + the status card on the Service page; in 2026-09 the status card moved from the Service page into the Dashboard as `ServiceStatusCard`, and the badge moved with it; on 2026-09-03 the badge was removed altogether as a redundant hint, while the "Restore Baseline" entry point stayed on the Parameters page status bar). It supports in-place "Restore Baseline" and "Clear Session Params", so users can tell "which baseline the current parameters deviate from" without entering the Parameters page.
23. **Hand-written modules vs mature libraries (2026-09-08 audit)**: after every hand-written module in the repo was assessed against a mature-library alternative, **two changes were adopted** — `structuredClone` replacing `JSON.parse(JSON.stringify())` for deep copy/serialization (**2026-09-20 verification: only partly landed** — the params session snapshot already uses `structuredClone` (stores/params.ts:298), but `useIPC.ts:23` and the preload's `clonePlain` (index.cjs:60) **still use `JSON.parse(JSON.stringify())`**, and the former carries a comment explaining why: structuredClone cannot clone a Vue reactive Proxy (DataCloneError); the original text claimed a complete replacement, which was an overstatement); and zod replacing the hand-written field-by-field validation in settings/presets (`normalizeSettings`/`parsePreset`, a declarative schema + a per-field `.catch()` fallback to the default, semantically equivalent to the original tolerant behavior). **Assessed and explicitly judged not worth replacing** (each with its own measured or engineering justification):
    - **Download / HF HTTP transport layer** (`download-manager.ts` / `huggingface-client.ts`) → got/axios: the BoringSSL TLS fingerprint of Electron's bundled Node is RST outright by hf-mirror.com, so an Electron `net`-based transport has to be injected (decision 13); got/axios cannot carry that injected transport and could only replace the non-Electron path, so the value is discounted.
    - **Device probing** (`devices.ts`) → systeminformation: it currently runs `llama-server --list-devices`, which is naturally consistent with the devices the engine can actually use; system-level GPU probing could mislead instead.
    - **Process / startup orchestration** (`process.ts`/`launcher.ts`) → execa: Windows process-tree cleanup (`taskkill /F /T`) and the Electron lifecycle are platform-specific implementations; `node:child_process` is already enough.
    - **URL parsing** (`url-parser.ts`): already uses the built-in `new URL()`; the `blob/tree/resolve` path-segment rules are HF/ModelScope-specific business logic, with no mature library covering them.
    - **GGUF** (`gguf-meta.ts`, 743 lines) → gguf.js: the parsing layer could indeed be covered, but suggested parameters / quantization mapping / chat-template matching are llama-server business inference that gguf.js cannot replace, and its format details carry a risk of drift.
    - **Logging** (`download-log.ts`/`cleanup-logger.ts`) → electron-log/winston: these are business-specific JSONL event logs (replay of download events), not general application logging.
    - **Path handling** (`paths.ts`): already `node:path`; **docs validation script** (`check-docs-links.cjs`): 131 links across 28 files — the in-house implementation is already light enough.
