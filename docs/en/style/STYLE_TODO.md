## Audit method (how to reproduce this list)

```bash
node scripts/style-audit.cjs      # or pnpm style:audit
```

22 checks are codified in `scripts/style-audit.cjs`; all green = consistent with the frontend.md §7.5 spec; ❌ findings print `file:line` detail and the script exits non-zero (so it can be wired into CI / pre-commit). What each check does:

1. bare colors inside components (token-only rule; `#fff`/`#1a1a1a` allowed only as text on colored buttons)
2. bare font sizes inside components (must go through `--fs-*`)
3. radii go through tokens (`2px` track / `50%` circle / `0` are the exceptions)
4. spacing scale (gap ∈ 4/5/6/8/10/12/14, `0` allowed; **there is no 1/2/3px micro-spacing tier — it always normalizes up to 4px**, see #16)
5. no duplicated scoped button classes (only the globally converged `action-btn`/`mini-btn`/`tab-btn`; component-specific classes such as `modal-btn`/`dl-btn`/`fb-btn`/`win-btn` may keep scoped styles, see §7.5.5; `ctrl-btn` disappeared along with "button text inlined", see #27)
6. shadows/overlays go through `--shadow-*` / `--overlay`
7. inventory of `backdrop-filter` usage sites (prints the list for manual review — is it limited to the glass layers / modal backplates allowed by §7.5.6? dropdowns and menus are solid now, see #41)
8. animation only touches transform/opacity (transitions on layout properties must carry `var(--dur-*)`)
9. semantic line heights (1 / 1.3 / 1.4 / 1.5 / 1.55 / 1.6; `normal` / `var()` pass through)
10. font weights restricted to 400 / 600 / 700 (`normal`=400 / `bold`=700 accepted as equivalents)
11. top-level selectors in non-scoped `<style>` blocks (a `<style>` without `scoped`) must contain at least one component-private class — never Arco global class names alone, otherwise a popup teleported to body hits other components globally (§7.5.6)
12. do not override Arco internal state classes (`.arco-*-checked` / `-active` / `-selected` / `-disabled` / `-current` / `-dragging` / `-expanded`) — they are brittle across Arco upgrades; express selected states through Arco's own states or the `color` prop instead
13. `a-progress`'s `:percent` must be a **0–1 ratio** — Arco's `line.js` renders `width: percent * 100 %`, so passing a percentage (any expression containing `* 100` or a `Pct`-style name) pins the bar to full; in practice this is exactly the "download progress bar doesn't match the real progress" symptom (#71)
14. Motion declarations use `var(--dur-*)` — literal durations and `infinite` are rejected (the `--dur-ambient` persistent-hint tier is the exception, see §7.5.7 / #90)
15. Elevation uses `var(--z-*)` — `0` / `1` / `auto` and stacking inside a single element are allowed (#90)
16. Keyboard reachability and naming, three parts: **16a** clicks only ever sit on Arco components (no self-drawn clickable elements), **16b** an `a-button` with only `#icon` must carry `aria-label` (a tooltip is not an accessible name), **16c** `a-modal` must carry `role="dialog"` + `aria-modal` (Arco 2.58 gives none of the three, see #84–#86)
17. Overwrites of Arco internal-state classes in the token layer (`styles/`) are registered one by one: `ARCO_STATE_ALLOW` matches a marker against an **expected line count**, so a registry that no longer equals reality turns red (#91)
18. `a-button` colours are never overridden: a selector that hits a class attached to `<a-button>` (or `.arco-btn*`) and declares `color` / `background` / `border` / `box-shadow` is reported; exceptions must be registered in `BTN_COLOR_ALLOW` with a `why` and an expected rule count (cause: the scoped `[data-v-*]` attribute freezes the hover text colour — see §7.5.1 / #93)
19. The light theme (a block whose top-level selector is exactly `body`) must not assign literal values to Arco's state colour tiers — the indirection `--danger-6: var(--red-6)` is where components pick their colour, so stepping it repaints alert / form validation / tag / progress / switch and everything else reading that tier, while in dark the same line never applies because `body[arco-theme='dark']` outranks it (see §7.5.1 / #95)
20. Writing colour onto an Arco internal node must be registered line by line: a selector containing `.arco-*` (or hitting a class attached to an Arco component) that declares `color` / `background` / `border` / `box-shadow` is reported — the button side belongs to check 18 and the token layer to check 17; exceptions go into `ARCO_COLOR_ALLOW` with a `why` and an expected count (17 entries, 23 rules, see #96)
21. The icon semantic table must be one-to-one and every name must have a reader (`components/common/icon-map.ts`): one Arco glyph mapped from several semantic names is reported (historical defect: `folder` and `folder_open` were both the plain folder, so "go up one level" and "open directory" looked identical), as is a semantic name with no reader in `ui/src` (delete the name and its import together); a wrong name is additionally caught at `vue-tsc` by the `IconName` type (see #97)
22. The console token family (`--log-kind-*` / `--console-*`) must be defined and have readers: an undefined `var(--x)` **silently falls back to the inherited colour** — the recorded case is 1e73a17 deleting the four level-colour definitions in `theme.scss` as if they were property overrides, killing console colouring outright while every existing "is the colour written correctly" check stayed green; this check verifies both directions for the family (every use has a definition, every definition has a reader) and self-proves its parse scale (fewer than 6 definitions found reports a deformed parser)

### 56. Selected row in the model table lost its color on hover (Arco's row-hover rule outranked the selected background) — 🟢 Fixed (2026-09-13)

- **Location**: `packages/ui/src/components/models/LocalModelsPanel.vue` (`:deep(.arco-table-tr.row-selected > td)` inside `.models-table`).
- **Description**: the selected row background `rgb(var(--primary-1))` was applied at specificity (0,4,1) only, so Arco's row-hover rule `.arco-table-hover:not(…) .arco-table-tr:not(…):hover .arco-table-td:not(…)` (0,9,0) overrode it with the neutral `--color-fill-1` the instant the pointer entered the row — the selection visually vanished while hovered, inconsistent with the rest of the app where a selected element keeps its color on hover (DownloadCard `.checked` / FileBrowserModal `.checked` do not fall back). The selected row now keeps its color while hovered; no new color introduced, no additional color difference added.
- **Verification**: `pnpm style:audit` all green; on the mock page (`127.0.0.1:5173/#/models`) hovering a selected row in either theme keeps the computed `td` background at `rgb(var(--primary-1))` (dark `rgb(0,13,77)` / light `rgb(232,243,255)`) instead of falling back to `--color-fill-1`.

### 57. Dark-theme selected row background was too dark (primary-1 resolves to a near-black navy; filling a whole row looks heavy) — 🟢 Fixed (2026-09-13)

### 58. Status tags passed semantic color names that Arco doesn't recognize to a-tag (success/warning/danger/processing) — 🟢 Fixed (2026-09-13)

- **Location**: `StatusTag.vue` (the `arcoStatus` map), `StatusBar.vue` (the `statusColor` map + the two "Copied" feedback tags).
- **Description**: Arco 2.58's a-tag presets are only the 13 physical color names (red/orange/green/…/gray); the semantic names `success`/`warning`/`danger`/`processing` are not recognized and fall into the custom-color branch — the inline `backgroundColor: 'success'` is invalid CSS and the browser drops it, so the tag was left with only the fallback background (light fill-2 #F2F3F5 / dark white at 8%) plus white text inherited from the status bar: unreadable in both themes (user feedback: "it looks terrible in both light and dark mode"). - **Fix**: the mapping now uses preset physical colors: `success→green` / `warning→orange` / `danger→red` / `processing→arcoblue` (`gray` was already valid). Arco preset tags ship their own light/dark treatment (light = pale background with dark text pill, dark = translucent color background with bright text).
- **Verification**: measured in the browser on the status bar's "Running" tag: light = `arco-tag-green` (background `rgb(232,255,234)` / text `rgb(0,180,42)`), dark = background `rgba(39,195,70,0.2)` / text `rgb(39,195,70)`; a repo-wide `grep` confirms no other semantic color name reaches a-tag (LocalModelsPanel tagColor/fitColor already use physical colors; DownloadCard statusColor is a plain text color, valid CSS).

### 82. `PageFrame` is not a flex column, so every `flex: 1` written by pages is dead → the log console grows without bound and its internal scrolling never works — 🟢 fixed (2026-10-06)

- **Location**: `packages/ui/src/components/common/PageFrame.vue:8-11` (`.page-frame { min-height: 100%; padding: … }`, no `display: flex`); affected consumers `pages/LogsPage.vue:179-214` and `styles 257-264,303-318` (both `.console-wrap` and `.console` declare `flex: 1; min-height: 0`).
- **Description (what actually happens)**: the log console on the logs page **never scrolls itself** — as logs accumulate it pushes the whole page into an outer scrollbar. Users think "auto-scroll to bottom" works, but that `scrollTop = scrollHeight` line acts on a box whose height always equals its content, so it does nothing; the "new logs" pill can therefore never appear on this page either, because the state "not scrolled to the bottom" does not exist inside that box.
- **Root cause (measured, not inferred)**: the computed style of `.page-frame` is `display: block` (Arco's `.arco-layout-content` provides only `flex: 1`, never `display: flex`), so `flex: 1` on its children has no flex context and their height degenerates to content-driven. Browser measurement (mock page, `.app-content` 705px tall inside the viewport): with 5 log lines `.console` is **159px** and `.app-content.scrollHeight` is **705**; after temporarily inserting 200 lines `.console` is **4187px**, `.app-content.scrollHeight` is **4353**, while `.console` itself reports `scrollHeight > clientHeight` as **false** and `scrollTop = 99999` still leaves it at **0**.
- **Fix direction and its price (must be decided before touching)**: ⚠ **making `.page-frame` `display: flex; flex-direction: column` is not enough — measured.** Tried on 2026-10-06 and re-measured: `.page-frame` did compute to `flex`, yet after inserting 200 lines `.console` was still **4187px**, `scrollHeight > clientHeight` was still **false**, and `scrollTop` still ended at **0**. The missing link is a **definite height**: `.app-content` is itself `display: block`, so the `flex: 1` Arco gives `.page-frame` is dead there too, `.page-frame` stays content-sized, and its children's `flex: 1` has no free space to distribute. A correct fix must do two things at once: (1) give `.app-content` or `.page-frame` a **definite height** (`height: 100%` — `.app-content` measurably has a definite height of 705px); (2) handle flex column's default `flex-shrink: 1` — on long pages (the params page, 60 rows) shrinking children would **clip content instead of overflowing into the scroll area**, so non-flexible children need an explicit `flex-shrink: 0`. **The price is app-wide**: switching block flow to a flex column stops adjacent margin collapsing, so vertical spacing on all seven pages can change, and rules such as `.tab-content { flex: 1 }` in `ModelsPage` that are dead today would become live and need per-page review. - **Fix (2026-10-06)**: all three skeleton layers got a definite height **and** a flex context at the same time — miss one and you are back to the shape disproved just above. (1) `.app-content` in `components/layout/AppLayout.vue`: add `display: flex; flex-direction: column` and change `overflow` from `auto` to `hidden` (Arco already gives this layer `flex: 1`, and its parent `.app-body` has a definite height, so that is where resolvability starts); (2) `components/layout/PageHost.vue`: `flex: 1 1 0%` plus a flex column, passing the height down; (3) `components/common/PageFrame.vue`: `min-height: 100%` replaced by `display: flex; flex-direction: column; flex: 1 1 0%; min-height: 0; overflow: auto`, **with `flex-shrink: 0` declared for its direct children** (`.page-frame > :deep(*)`) — that is precisely the clipping risk predicted above: on a long page (the params page, 69 controls) a compressed child is content you can neither see nor scroll to. Two extra measurements shaped the details: `overflow` stays `auto` on **both** axes, because writing `overflow-x: hidden` measurably cut the params page status row's button cluster (`scrollWidth 714 > clientWidth 597`) out of reach; and two rules whose `flex: 1` was previously dead would suddenly become live and shrink by one step, so they now read `flex: 1 0 auto` (grow only, never compress) — `.tab-content` in `ModelsPage.vue` and in `SettingsPage.vue`. Test support added to `dev/demo-mock.ts`: `globalThis.__mockPushAppLog(n)` (following the existing `__mockExternalServer` pattern — the guard needs "far more than one screen" of logs, while the initial buffer holds 5 entries and the real push cadence is not under test control) and a `?lang=en` boot shape (mock settings are not persisted, so switching language in the UI reverts to Chinese on reload).
- **Verification after fixing** (measured): with 400 entries pushed onto the logs page the `.console` height stays **539px regardless of row count**, `scrollHeight 6602 > clientHeight 537`, and assigning `scrollTop = 99999` **settles at 6065** (before the fix it was permanently 0, i.e. the auto-scroll was spinning in place); the "new logs" pill now actually appears on this page (structurally impossible before, since the box could never be "not at the bottom"), and `.console` has the same height with the pill shown or hidden (absolute positioning — no jump). All seven pages measured in both languages: horizontal overflow **0px**, long pages scroll to the bottom inside `.page-frame` (params page `scrollTop` reaches 3418), the outer `.app-content` is no longer stretched, and the built-in Web UI iframe fills 661px. The behaviour is now pinned by `e2e/web/logs-scroll.spec.ts` (5 cases per language, including a **deletion experiment**: reverting the skeleton to block flow makes the console grow with content, removes internal scrolling and puts `scrollTop` back to 0 — all three assertions turn red). `pnpm e2e:web` green at 40 cases.

Category and quantization do have adjacent hues (`cat-gguf` purple ↔ `quant-i` violet, `cat-safetensors` green ↔ `quant-fp16` green), judged acceptable because the two families sit in fixed positions and **always carry text labels** (`GGUF` vs `Q4_K_M`); hue orthogonality is not pursued.
